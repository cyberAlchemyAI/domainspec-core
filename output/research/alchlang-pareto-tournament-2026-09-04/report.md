# Pareto Tournament research result

## Verdict

The method is suitable for an AlchLang UX experiment, with two constraints:

- the existing browser benchmark remains an eligibility gate;
- the Pareto tournament selects a trade-off frontier, not a universally best
  interface.

This is materially better than adding a single density score. A weighted score
could silently decide that shorter pages compensate for worse comprehension or
lost language coverage. Pareto dominance makes that trade visible.

## What exists now

Candidate `56c922798bbe45a51eda66619362b0add578187289baee421ede77e29c239b2b`
has zero blocking browser findings. Its complete tutorial is approximately
24.3 viewport heights on desktop and 37.5 on mobile. The present benchmark can
detect breakage, but it has no comparative candidate model and cannot establish
whether that length is useful depth or avoidable overload.

## Research basis

- Deb et al.'s NSGA-II work provides the non-dominated sorting and frontier
  preservation model used here:
  <https://homes.cs.washington.edu/~sagarwal/nsga2j.pdf>
- ParetoAdapt applies a posteriori preference to UI adaptation and explicitly
  identifies sensitivity in weighted-sum objective formulations:
  <https://cix.cs.uni-saarland.de/?page_id=420>
- Preference-Guided Multi-Objective UI Adaptation supplies recent primary
  evidence for human-in-the-loop preference guidance over UI Pareto fronts:
  <https://static.siplab.org/papers/uist2025-preference-guided-ui-adaptation.pdf>
- Abel et al. empirically compare pairwise preference elicitation with
  constrained optimization; this supports testing the comparison interaction
  itself rather than assuming it is effortless:
  <https://onlinelibrary.wiley.com/doi/full/10.1111/itor.12907>
- WCAG 2.2 remains a standards source for accessibility constraints and must
  stay outside subjective tournament voting:
  <https://www.w3.org/TR/WCAG22/>

## First live experiment

Use four immutable variants: baseline, compact spacing, progressive reference,
and task first. Each treatment changes one design family only.

For every variant:

1. Run the existing production-build Firefox benchmark.
2. Exclude hard-gate failures without assigning them a preference score.
3. Run the same four task cards with counterbalanced candidate order.
4. Record completion, time, wrong turns, comprehension answers, required
   meaning retained, viewport traversal, and pairwise choice with ties.
5. Compute epsilon-Pareto layers from separate objectives.
6. Show the owner the non-dominated frontier with trade-offs and uncertainty.

A six-to-eight-person calibration pilot can test the procedure and expose bad
tasks, but cannot support a population-level usability claim. A later sample
size must follow observed variance and the intended decision confidence.

## Why this can fail

- With too many objectives, almost every variant can become non-dominated.
- Synthetic or model-generated preferences cannot replace user evidence.
- Pairwise choices can cycle and depend on order or task framing.
- Page height is only a density proxy; shorter is not intrinsically better.
- Bradley-Terry-style latent rankings require assumptions that must be checked;
  the first implementation should preserve raw matches and ties even if a
  ranking model is added later.

## Prototype result

`prototype.mjs` is a run-local deterministic implementation of eligibility,
epsilon dominance, Pareto layers, and frontier round-robin scheduling.
`fixtures.json` clearly separates real baseline observations from synthetic
calibration values. `fixture-result.json` is generated by executing the
prototype.

The prototype proves only that the proposed algorithm handles the designed
fixtures. It does not prove that any UX variant improves the product.
