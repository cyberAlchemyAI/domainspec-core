# CyberAlchemy Lab game-like canvas research strategy

## P1 trigger decision

This is a governed research dispatch. It must synthesize current product bytes, four runtime choices, official package and license evidence, human-interface standards, accessibility constraints, prior CyberAlchemy research, and adversarial collapse tests. The raw evidence and competing lenses are large enough to justify context protection, isolation, synthesis, and parallelism.

## Intended result

The dispatch will decide whether the current Cutaway Research Tower should use Phaser, PixiJS, Excalibur, or a native DOM/SVG/Canvas approach for its first real spatial game layer. It will produce an exact-bound `findings.md` with one selected hybrid architecture, a no-engine fallback, typed state/event boundaries, a finite L0 playable slice, proposed implementation boundaries, and validation obligations.

It will not install a dependency, write product code, create assets, mutate the API or tests, run workers, promote ontology, publish, deploy, release, or establish human benefit or production readiness.

## Lanes, groups, and subagents

### Group 1 — explorers, parallel

Anti-bias axis: official runtime evidence versus human-interface evidence versus exact local implementation evidence.

- **Hewitt, Carl — runtime explorer.** Compares native DOM/SVG/Canvas, Phaser, PixiJS, and Excalibur using current official documentation, repositories, releases, manifests, and licenses. Output: versioned capability and risk matrix plus smallest engine spike.
- **Alexander, Christopher — human-interface explorer.** Tests pan/zoom, room entry, moving robots, hotspots, minimap, motion, keyboard, and fallback behavior against primary standards and bounded local research. Output: intervention/claim/witness matrix with human residue.
- **Turing, Alan — repository integration explorer.** Traces the exact current HTML, witness loader, package, server, assets, tests, and validation receipt. Output: compatibility map, bridge/state contracts, file boundaries, failure fallback, and finite first playable slice.

Every pair has one predicted-disagreement record in `dispatch-sheet.json`. Together the three lanes cover the engine choice, human boundary, and implementation feasibility without asking one agent to dominate all three.

### Group 2 — synthesizer, sequential

- **Simon, Herbert — synthesizer.** Reconciles all explorer returns into a candidate decision: selected runtime or native fallback, hybrid canvas/DOM architecture, state and event vocabulary, prototype slice, performance/accessibility/failure contracts, staged roadmap, and killed alternatives.

### Group 3 — reviewers, parallel after synthesis

Anti-bias axis: precedent, non-vacuity, and definitional soundness.

- **Rittel, Horst — precedent skeptic.** Verifies package owners, versions, licenses, maintenance, browser primitives, and existing local ownership.
- **Kahneman, Daniel — non-vacuity skeptic.** Requires a finite playable witness with negative controls, frame/input/layout/focus/state checks, semantic fallback, and honest human-proof ceilings.
- **Capucci, Matteo — definitional skeptic.** Prevents collapse among animation, renderer, game engine, world state, evidence state, ontology, robot avatar, real worker execution, and authority.

The synthesizer and reviewers may use one bounded zig-zag. One feedback edge may reopen explorers only for missing primary evidence.

### Group 4 — writer, sequential after exact-binding evidence closure

- **Shannon, Claude — findings writer.** Writes only `findings.md`. The strategist, not the writer, mechanically assembles verbatim explorer returns into `research.md`.

### Group 5 — auditor, final sequential gate

- **Brandenburg, Martin — auditor.** Accepts or returns one bounded writer revision. The parent remains the final approver.

## Dependency flow

```text
explorers (3 parallel)
        |
        v
synthesizer <---- one missing-evidence feedback ---- explorers
        |
        v
reviewers (3 parallel) ---- one bounded zig-zag ---- synthesizer
        |
        v
exact-binding evidence closure
        |
        v
writer ---- one bounded revision ---- auditor
        |
        v
parent final approval and closeout
```

The evidence-closure contract is `exact-binding`: every load-bearing engine or browser claim needs a primary-source identity and selector; every local recommendation needs an exact file digest or selector. The writer remains blocked while a required row is unresolved.
