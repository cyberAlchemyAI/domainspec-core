# Invoke Define - Branch Materialization Target

## Definition

The refined Ontologize view-triad method should define a view as a **materialization of ontology branches**:

```text
view = a governed projection of B1 meaning, B2 system, B3 run-context, and B4 bridge into an artifact layer whose authority is explicit
```

This changes the current pack from a generic "produce system-view, engineer-view, ontology-view" method into a branch-aware method:

- system-view materializes branch shape and branch tensions;
- engineer-view materializes branch-boundary decisions and enforcement mechanics;
- ontology-view materializes typed branch nodes, bridge edges, and forbidden branch relationships.

## Acceptance Checks

| Branch | Required Materialization Check |
| --- | --- |
| B1 meaning | The view identifies the intended policy, rule, value claim, or outcome without confusing it with implementation. |
| B2 system | The view identifies the implementation/runtime evidence that realizes, observes, tests, or violates B1. |
| B3 run-context | The view identifies the bounded run denominator and lifecycle context; B3 cannot be a footnote. |
| B4 bridge | The view identifies the bridge edge or evidence relation connecting branches, including drift or contradiction route when present. |

## Route Menu Decision

Selected route: constrain the existing triad.

Rejected route: add a new upstream branch-view artifact.

Rationale: `ONTOLOGY-BRANCHES.md` already exists as the branch explanation source. Adding another branch-view layer risks duplicating it. The method should instead make the existing three views consume and materialize branches with explicit gates.

## Design Tension For Dialectic Review

- The novel side argues branch materialization needs a stronger matrix/gate model so B3/B4 do not disappear behind generic "context" and "ontology" language.
