# Roadmap Lab Implementation Layering Seed

This seed records the design's value order. Invoke plan expands it into the
governing L0–L3 artifact; it does not schedule work here.

| Layer | Decision to unlock | Smallest proof | Main deferral |
| --- | --- | --- | --- |
| L0 | Can a newcomer understand FPR-01 and submit one durable, correctly bound proposal? | One generated learning packet, restatement, source request, proposal event, and visible submitted state through existing Canvas. | All-node coverage, owner automation, collaboration. |
| L1 | Can the learning/proposal model repeat across roadmap nodes and revisions without target drift? | Validated copy/field coverage, proposal history, stale detection, restart and representative node classes. | Direct lifecycle effects, remote identity. |
| L2 | Can governance and degraded behavior hold when proposals route to different owners or fail? | Owner classification, fail-closed unsupported action, explicit review handoffs, retry/replay/error evidence. | Production authorization, scale, generic source browser. |
| L3 | Does one real newcomer find the surface useful, and can one accepted copy proposal close the loop with evidence? | Victor trial plus one owner-accepted presentation-copy rebuild/republish round trip. | General release, multi-user operation, graph/Craft auto-mutation. |

Layer boundary sentence:

> After each layer, we know whether its decision is supported by retained
> evidence; otherwise we stop, narrow, or redesign before promotion.

Recommended first unit: define the presentation-copy and interaction payload
oracles before changing the builder or UI. All later behavior depends on stable
field identity and proposal bindings.
