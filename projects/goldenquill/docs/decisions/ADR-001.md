# ADR-001: v0.1 Substrate Selection

**Status:** LOCKED (2026-04-19, architecture v7 + v10 Appendix D)
**Decision date:** 2026-04-14 (initial), 2026-04-19 (final lock with A1-A12)
**Decided by:** Josh Inklovich

## Context

Tilth v0.1 needs a substrate stack that runs on client-owned hardware (128 GB production, 8 GB dev), supports a six-seat agentic pipeline (Scout, Scribe, Editor, Judge, Red Team, Logician — per v7.0.6 SELF-LOCKED 2026-05-09) with deterministic validation gates, preserves client sovereignty (no cloud lock-in, no data exfiltration), and can be maintained by a solo operator who does not code.

The substrate must handle: multi-model orchestration across provider families, structured output validation, document skill management, local inference for cost-sensitive seats, observability without cloud dependency, and offline prompt/card refinement.

## Decision

The v0.1 substrate is:

| Layer | Choice | Role |
|-------|--------|------|
| **Orchestration + structured output** | Pydantic AI | Multi-model orchestration, type-safe seat I/O, schema enforcement, structured LLM output parsing — replaces both LangGraph (orchestration) and OpenClaw (document substrate) with less code and fewer dependencies |
| **Observability** | Logfire | Tracing, metrics, pipeline run inspection — Pydantic-native integration |
| **Local inference** | Ollama or vLLM | OpenAI-compatible endpoint for Scout (mistral:7b) and future local models |
| **Offline refinement** | DSPy + GEPA | Card refinement and Library development — offline only, not in the live pipeline |

### Why Pydantic AI covers orchestration

LangGraph was originally in the substrate for orchestration, and OpenClaw for document/skill management. Both were removed. Pydantic AI handles what both did — structured multi-model seat invocation, type-safe I/O between pipeline stages, validation, and agent lifecycle management — with less code and a single dependency chain. The pipeline orchestration lives in a custom `run_pipeline` module (Section 5) that composes seat runners, revision loops, rate limiters, and state checkpoints using Pydantic AI primitives. ~930 LOC, fully tested, no framework overhead.

## Alternatives Considered

### Orchestration + structured output

- **LangGraph** — Initially selected for orchestration. Removed. Added dependency complexity without proportional value for a pipeline that is fundamentally linear (Scout → Scribe → Editor → Judge, with Logician wrapping each). Pydantic AI's agent primitives handle the same seat-invocation and state-passing patterns with less code. LangGraph's graph topology abstraction doesn't map to Tilth's linear pipeline with revision loops.
- **OpenClaw** — Originally selected as the document substrate (skill/document management). Removed. Pydantic AI's structured output and validation capabilities cover the same ground — type-safe document schemas, structured skill invocation, validation gates — without a separate dependency. OpenClaw's curated/frozen model was sound, but Pydantic AI absorbs the role.
- **CrewAI / AutoGen** — Evaluated early. Too opinionated about agent communication patterns. Tilth's council pattern (explicit file paths between seats, clean output rule) doesn't map cleanly to their abstractions.
- **LangChain** — Rejected across the board (output parsers, document loaders). Too many abstraction layers. LangChain assumes you want flexibility; Tilth wants strictness. Pydantic AI does what we need natively.
- **Instructor** — Strong contender for structured output. Pydantic AI won because of Logfire integration and because it handles the full seat invocation lifecycle, not just output parsing.

### Local inference

- **llama.cpp direct** — Rejected. Ollama wraps it with a clean API and model management. No reason to go lower.
- **LocalAI** — Evaluated. Ollama has better Apple Silicon support and simpler model pulling. vLLM is the alternative for GPU-heavy production hardware (DGX Spark).
- **No local inference (all cloud)** — Rejected on sovereignty grounds. Scout's discovery loop runs frequently; cloud-only would mean API costs scale with search frequency and create a cloud dependency for the most basic function.

### Observability

- **OpenTelemetry direct** — Would work but requires more setup. Logfire's Pydantic-native integration means structured output validation and tracing share the same type system.
- **Weights & Biases / MLflow** — Cloud-first tools. Violate sovereignty principle.
- **No observability** — Not an option. A pipeline that can't be inspected can't be trusted.

### Offline refinement

- **Manual prompt tuning** — The baseline. DSPy + GEPA automate Card refinement against rubric libraries, which is more systematic than hand-tuning.
- **Online fine-tuning** — Out of scope. BYOK model providers don't support fine-tuning through their APIs in a way that preserves sovereignty.

## Consequences

- The substrate is locked for v0.1. Proposals to swap components require a new architecture audit round.
- Pydantic AI as the single orchestration + validation layer means fewer dependencies to audit and fewer integration boundaries where bugs hide. The tradeoff is tighter coupling to the Pydantic ecosystem — acceptable given Logfire's native integration.
- Ollama on 8 GB dev hardware limits local inference to 7B-class models. Production hardware (128 GB) can run much larger models locally, reducing cloud API dependency further.
- DSPy + GEPA are offline-only tools. They improve the pipeline's prompts and cards between runs, not during runs. This is intentional — the live pipeline uses fixed, audited prompts.
