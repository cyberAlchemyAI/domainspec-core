Awaken The Harness

A repository is not just files. It is a living negotiation between intent, implementation, decisions, tests, telemetry, and the people trying to keep all of that coherent.

Necronomicon gives that negotiation a local harness. It maps ontology, carries session memory, routes requests through selected capabilities, and records the reasons behind each handoff.

Core Thesis

State is not authority. Session files preserve working memory, but canonical truth remains in source documents, registries, code, tests, and reviewed evidence.

The Two Names

Necronomicon has two operational faces. The first is a direct ontology spell. The second is a persistent session spell that keeps repository work coordinated over time.

Surface Canonical Contract Use It For
arcanum-necronomicon ontology-harness Ontology maps, premise review, confidence promotion, session distillation, branch-aware business/system mapping, and bridge validation.
arcanum-necronomicon-session necronomicon-session Durable repository sessions, selected capability routing, fallback discovery, capability updates, decisions, route ledgers, and handoffs.
The old mistake was treating Necronomicon as a copied runtime book. The corrected model treats it as a harness: it may hold memory and manifests, but not duplicated canonical sigil or spell definitions.

The Knowledge Substrate

Necronomicon only becomes useful when it can tell the difference between raw evidence, generated synthesis, governing assumptions, and decisions. That is the substrate beneath the session harness.

Inventory gives the harness reusable source-grounded context. Ontology gives that context roles, edges, confidence, and branch ownership. Axioms and premises name the commitments that future work must either honor, test, revise, or retire.

Authority Ladder

  • Raw sources remain immutable evidence.
  • Inventory pages are generated, reusable maps.
  • Ontology assigns roles, edges, and confidence.
  • Axioms and premises carry explicit commitment weight.
  • Decisions change behavior only when recorded and approved.

Inventory

The compiled knowledge layer. It indexes sources, concepts, workflows, architecture, tests, observability signals, contradictions, and open questions.

Ontology

The role and relationship map. It separates business meaning, system reality, bridge evidence, drift, and traceability gaps.

Axioms

The load-bearing truths and constraints that steer work until evidence revises them. They should be visible, testable, and demotable.

Premises

Working bets under review. A premise can be promoted, revised, split, demoted, retired, or escalated to a decision gate.

Confidence

Two separate signals: evidence confidence asks how well a claim is supported; commitment confidence asks how deeply the project should rely on it.

Bridge Evidence

Links between intent and implementation: realized by, tested by, observed by, constrained by, traced to, depends on, or drifts from.

Layer Question It Answers Necronomicon Use
inventory What do we know, where did it come from, and can we reuse it? Feeds context lookup, routing evidence, and source-grounded summaries.
ontology-vault What roles, relationships, confidence states, and gaps exist? Maps sessions, premises, conventions, branch ownership, and bridge edges.
axioms Which truths or constraints are currently load-bearing? Guards routing, implementation, and promotion against hidden assumptions.
premises Which working bets still need evidence, contradiction review, or decision? Creates premise-review and confidence-promotion work for the ontology harness.
decisions What did a human or governance gate actually choose? Separates approved commitments from session memory and agent synthesis.

The Session Loop

A Necronomicon session turns a conversation into a controlled repository loop. Each step has a narrow job, so memory stays useful and capability changes remain auditable.

1
Start

Create a session, name the objective, and choose capability scope.

2
Load

Read memory, decisions, recent routes, and selected commands.

3
Route

Prefer explicit or selected local Arcanum capabilities.

4
Fallback

Offer Arcanum candidates when no selected command fits.

5
Update

Add, remove, refresh, or author capabilities only when approved.

6
Close

Write route summary, memory, decisions, validation, and handoff.

The Spellcraft Surface

In Arcanum, a sigil is an atomic capability. A spell is a composed workflow that gives those capabilities a shared state, sequence, gate model, and output contract.

Necronomicon Session is spellcraft in action: it uses ontology, context retrieval, inventory, task execution, decisions, runtime installation, and maintenance signals as a coordinated repository harness.

The craft is not just choosing commands. It is deciding which knowledge layer should speak: inventory for reusable evidence, ontology for meaning and relationships, axioms for constraints, premises for review, and decisions for approved commitments.

Creation Rule

If fallback discovery repeatedly finds the same missing move, Necronomicon should not improvise forever. It should propose a capability update, a new spell, or a reusable sigil.

Capability Role In The Tour
ontology-harness Maps ontology, premises, axioms, confidence, branches, and bridge evidence.
inventory Maintains reusable source-grounded knowledge so sessions do not rediscover the same context.
ontology-vault Distills sessions, reviews premises, proposes conventions, and validates confidence gates.
necronomicon-session Holds durable repository memory, routing, updates, and handoffs.
context-builder Retrieves compact evidence for routing, resume, and execution.
task-session Executes one bounded task with decisions, gates, and validation.
decision-gate Resolves consequential trade-offs before mutation.
sigil-runtime-installer Refreshes runtime command surfaces after capability changes.
spellcraft and sigil-development Create new reusable workflows when the harness finds a missing pattern.

The Routing Table

Necronomicon is useful because it does not route every request from scratch. It starts from the selected capability manifest, then expands outward only when the repository lacks the right local move.

Priority Route Source Confidence
1 Explicit runtime command, exact spell ID, exact sigil ID, or exact alias. High
2 Selected Necronomicon capabilities by trigger, mode, or description. Medium to high
3 Ontology, vault, premise, confidence, branch, or bridge triggers. Medium
4 Arcanum registry fallback candidates that are not selected yet. Low until approved
5 Focused clarification when multiple credible routes tie. Blocked until resolved
Fallback discovery is an offer, not a silent install. The harness asks before adding a capability to the selected manifest.

The Memory Vault

The local Necronomicon folder is a vault for working state. It helps a repository session survive interruption, handoff, and repeated routing, while keeping canonical definitions somewhere else.

Memory should record the shape of knowledge, not replace it: inventory references source evidence, ontology records roles and bridge edges, axioms preserve load-bearing constraints, and session notes capture what changed during the run.

Path What It Holds
.arcanum/necronomicon/capabilities.json Selected sigils, selected spells, runtime commands, and fallback policy.
.arcanum/necronomicon/sessions/<id>/memory.md Durable summary of the active objective, facts, decisions, and next action.
.arcanum/necronomicon/sessions/<id>/routes.jsonl Route attempts, candidates, selected command, confidence, result, and validation.
.arcanum/necronomicon/sessions/<id>/decisions.md Resolved choices, open questions, assumptions, and blocked trade-offs.
.arcanum/inventory/ Reusable source-grounded entries, indexes, tags, contradictions, and query syntheses.
.arcanum/ontology/ Ontology maps, branch classifications, premise reviews, bridge validation, and confidence reports.
.arcanum/necronomicon/sessions/<id>/handoff.md Resume-ready summary for the next agent, operator, or session.
.arcanum/observability/ Telemetry for command use, route misses, validations, and follow-up signals.

Example Session Run

Imagine a repository where the team wants to add a governed onboarding workflow. The user does not want a loose conversation; they want durable memory, selected command routing, evidence lookup, and an auditable handoff.

1. Start

Create the session and select a compact capability set.

arcanum-necronomicon-session start
Objective: design a governed onboarding workflow
Capabilities: ontology-harness, inventory, context-builder,
task-session, decision-gate

2. Load Substrate

Inventory and ontology provide source-grounded context.

Read .arcanum/necronomicon/capabilities.json
Lookup onboarding docs in .arcanum/inventory/
Map actors, rules, premises, and bridge gaps with ontology-harness

3. Route Work

The request becomes a bounded task with evidence obligations. 

arcanum-necronomicon-session route \
  "turn the onboarding premise into a scoped implementation task"

Selected route: task-session
Context support: context-builder
Gate support: decision-gate

4. Handle Missing Capability

Fallback discovery suggests a capability without silently adding it. 

Route miss: no selected glossary capability
Fallback candidates: feature-glossary, spellcraft
Decision: add feature-glossary after this run
Report: .arcanum/necronomicon/capability-updates/...

5. Close

The session writes resumable state instead of relying on memory alone. 

arcanum-necronomicon-session close

Writes:
- sessions/<id>/memory.md
- sessions/<id>/routes.jsonl
- sessions/<id>/decisions.md
- sessions/<id>/handoff.md
The point of the session is not that every action happens inside one command. The point is that every action is routed through a visible harness: selected capability, evidence source, confidence, decision, output, and handoff.

Try The Invocation

The practical surface is intentionally small. One command handles direct ontology work. One command handles durable session work.

arcanum-necronomicon Run the Ontology Harness for mapping, premise review, session distillation, or bridge validation.
arcanum-necronomicon-session start Create a durable repository session with memory and selected capability routing.
arcanum-necronomicon-session route <request> Route a request through selected local commands before considering fallback candidates.
arcanum-necronomicon-session update-capabilities Add, remove, refresh, or author capabilities with an auditable update report.
arcanum-necronomicon-session close Write final memory, decisions, route history, validation, and handoff.
The balanced strategy is simple: use narrative for orientation, tables for dense facts, and command examples for action. Readers can skim the tour or follow it as a working model for their own repository harness.
