# Source Digest: Necronomicon Knowledge Substrate

Sources:

- [Necronomicon README](../../../arcanum/spells/necronomicon/README.md)
- [Knowledge Substrate Flow](../../../arcanum/spells/necronomicon/development/KNOWLEDGE-SUBSTRATE-FLOW.md)

Ledger: [../source-ledger.md](../source-ledger.md)

## Why This Source Matters

Necronomicon provides the repository harness model: memory, routing, active interaction, side notes, checkpoints, inventory UX, and promotion boundaries.

It is the daily operating shell that helps CyberAlchemy remember work without letting memory become authority.

## Compiled Concepts

### Repository Harness

Necronomicon creates a repository-local harness session with:

- setup profile;
- durable working memory;
- route history;
- checkpoints;
- bounded research workflows;
- maintenance recommendations;
- selected capability routing.

It coordinates capabilities but does not own their authority.

### Day-To-Day Loop

The everyday loop is:

```text
open repo
  -> recover context
  -> route request
  -> execute through owner
  -> checkpoint facts, decisions, contradictions, and gaps
  -> propose maintenance when repeated misses accumulate
```

### Active Interaction

Active interaction prevents every user turn from being classified from scratch.

The harness tracks:

- owning capability;
- active mode;
- status;
- pending prompt;
- expected response shape;
- continuation policy;
- handoff target;
- side note queue.

### Side Notes

Side notes preserve useful material without derailing the active flow.

They may become:

- active artifact input;
- durable project fact;
- research idea;
- related unblocker;
- contradiction;
- governance claim;
- reminder.

### Authority Ladder

The knowledge substrate defines the main authority flow:

```text
raw interaction
  -> session evidence
  -> discovery baseline
  -> inventory knowledge
  -> ontology candidate
  -> reviewed premise
  -> confidence decision
  -> constitution or axiom
  -> bridge-validated operating context
```

Necronomicon can collect, remember, and route. It cannot promote by itself.

## Inventory UX

Necronomicon should expose inventory through:

| Motion      | Meaning                                                                       |
| ----------- | ----------------------------------------------------------------------------- |
| Inventorize | Keep durable findings so they are not rediscovered later.                     |
| Retrieve    | Ask what the repository already knows before broad search.                    |
| Reconcile   | Preserve conflicts and route consequential contradictions to ontology review. |

## CyberAlchemy Adaptation

Memory and inventory must work together:

```text
memory gives continuity
inventory gives reusable evidence
ontology gives governed meaning
context-builder gives task focus
```

User workflow memory belongs behind a privacy and promotion boundary.

## Candidate Ontology Claims

| Claim                                                                    | Branch               | Candidate Entry                                |
| ------------------------------------------------------------------------ | -------------------- | ---------------------------------------------- |
| Memory preserves continuity but does not become authority.               | memory               | `rule-memory-continuity-not-authority`         |
| Side notes should be captured without derailing active interaction.      | memory               | `memory-pattern-side-note-queue`               |
| Necronomicon routes knowledge candidates but does not promote them.      | knowledge-governance | `rule-harness-candidate-only`                  |
| Inventory has three user motions: inventorize, retrieve, reconcile.      | memory               | `inventory-ux-three-motions`                   |
| Active interaction should continue the current owner unless interrupted. | operational          | `route-policy-active-interaction-continuation` |

## Tensions And Promotion Gaps

- User workflow model needs privacy policy before ontology use.
- Side note classes need a schema before they can feed inventory consistently.
- Harness memory should not become a shadow ontology.

## Agent Payload

Before using memory as evidence, ask:

```text
Is this only local continuity?
Is it a durable project fact?
Does it need inventory?
Does it imply ontology governance?
Does it touch user privacy?
```
