# Findings: CyberAlchemy Thinking Method Ontology

Dispatch id: `2026-06-18-cyberalchemy-thinking-method-ontology`

Status: research finding, not canonical ontology mutation.

## Direct Answer

Treat the CyberAlchemy method ontology as a small reuse map of already named primitives plus a few schema-backed witnesses for run context, bridge evidence, promotion state, invocation feedback, and maintenance triggers.

The first ontology move is not to canonize the whole loop `define -> research -> design -> plan`. The first move is to make each method claim pass a witness test: it needs an ontology entry, schema, register, fixture, card, or explicit source-backed gate before it can guide agents.

Ontologize synergizes with this work by acting as the product and schema pressure surface. CyberAlchemy names and governs method primitives; Ontologize proves whether those primitives can survive as branch-specific records, DAG edges, B3 run-context denominators, B4 bridge ledgers, branch materialization registers, optimization-chain claims, and buyer-readable proof artifacts.

## Honesty Contract

Use these labels in the method ontology:

| Label | Meaning |
| --- | --- |
| `BUILT` | A concrete file, schema, register, card, fixture, or implementation witness exists. |
| `OWNED` | A governing source already owns the primitive or rule. |
| `BUILD-FROM-OWNED` | The label is useful, but it is a projection or composition of owned primitives. |
| `PROPOSED` | Useful candidate, but missing a concrete witness or owner route. |
| `OPEN` | Requires owner decision, schema design, or execution proof before reuse. |

Rules:

- Do not list a candidate as a method primitive without a witness.
- Do not treat telemetry, reflection, or subagent synthesis as authority.
- Do not promote a candidate by wording alone.
- Do not create a new vocabulary term when an owned CyberAlchemy, Arcanum, or Ontologize term already carries the meaning.
- If a claim will guide agents, it needs status, evidence, confidence, owner, use scope, contradiction path, and maintenance route.

## Research Strategy

### Phase 1: Taxonomy First

Build a small method taxonomy with six lanes:

1. Epistemic lifecycle: define, research, design, plan, execute, validate, reflect.
2. Governance level: signal, evidence, candidate, premise, policy, constitution, axiom.
3. Confidence and authority: evidence confidence, commitment confidence, owner, use scope, contradiction path.
4. Run and feedback: invocation envelope, run context, telemetry, reflection, maintenance trigger.
5. Bridge and drift: raw drift, adjudicated contradiction, bridge ledger, branch materialization.
6. Ergonomics and translation: navigable surfaces, artifact state, proof sentences, buyer-facing summaries.

Deliverable:

- One taxonomy table with status labels, owner, witness path, allowed use, and collapse target.

### Phase 2: Schema Witnesses

Use existing schema-backed witnesses before inventing new records:

- `B3 Run-Context Record`
- `B4 Bridge Ledger`
- `Branch Materialization Register`
- `PromotionRecord`
- `Observed Invocation Loop Result`
- `Ontology Entry Model`
- Ontologize ontology-node schema
- Ontologize optimization-chain method schema

Deliverable:

- A method-witness matrix that maps each candidate primitive to a concrete schema, register, card, fixture, or source line.

### Phase 3: Distill Entries

Create only the first high-value ontology entries:

1. `route-before-work`
2. `trace-before-promotion`
3. `candidate-not-authority boundary`
4. `run-context denominator authority`
5. `drift-vs-contradiction separation`
6. `thick-entry-not-pointer`
7. `Branch Materialization Register`, explicitly scoped as method-local evidence

Deliverable:

- Candidate entries using `cyberAlchemy/agentic-system-ontology-entry-model.md`.
- Each entry must include evidence, intuition, agent payload, edge links, confidence, promotion state, and maintenance cues.

### Phase 4: Ontologize Pressure Test

Use Ontologize as the testbed:

- Can a method primitive become an Ontologize node, edge, run-context record, bridge ledger item, or optimization-chain field?
- Can it support B3/B4 branch evidence without collapsing operational ontology into run context?
- Can it produce a buyer-facing proof sentence downstream without becoming authority itself?

Deliverable:

- One dogfood card that traces:
  source evidence -> inventory row -> ontology candidate -> PromotionRecord -> B3/B4 witness -> translation sentence.

### Phase 5: Governance And Promotion

Promote only after owner route:

- Candidate entries stay visible as candidates.
- Promotion requires `PromotionRecord`.
- Constitution and axiom labels require stronger tests:
  - Constitution: governs form/model/allowed transformations/review gates.
  - Axiom: invariant-bearing, dependency-bearing, contradiction-reviewed, explicitly committed.

Deliverable:

- Promotion checklist for method primitives.
- Owner matrix for method entries, schema projections, translation artifacts, and runtime feedback.

## Synergy With Ontologize

CyberAlchemy and Ontologize should not merge into one ontology. They should form a governed loop:

| Layer | CyberAlchemy role | Ontologize role |
| --- | --- | --- |
| Method primitive | Names governance moves such as route-before-work and trace-before-promotion | Tests whether the move survives in concrete branch evidence |
| Schema | Provides ontology entry model, PromotionRecord, authority ladder | Provides B3/B4 records, branch register, DAG edges, optimization-chain schemas |
| Confidence | Splits evidence confidence from commitment confidence | Carries confidence through node/edge/card metrics |
| Drift | Keeps raw drift and candidate status honest | Implements `drifts_from`, `contradicts`, B4 bridge ledger, and branch materialization |
| Feedback | Uses OIL/reflection as candidate-generating feedback | Turns feedback into domain/product evidence only through schemas and gates |
| Ergonomics | Names navigable work surfaces and artifact-as-state as candidates | Tests whether proof sentences, cards, and scorecards make them real |

Practical integration:

- CyberAlchemy provides the "how we think" governance language.
- Ontologize provides the "can this be represented, measured, contradicted, and reused" pressure.
- Subagent strategy provides the research fanout and bias gates.
- PromotionRecord prevents subagent synthesis, telemetry, or buyer-facing copy from becoming authority without review.

- maintenance cue.

## Open Decisions

- Branch-as-view remains proposal-stage; the current witnessed materialization is still view-triad/B3/B4/branch-register based.
- Feedback vocabulary is split across OIL, signal-observer, execution-feedback, and ontology lifecycle. Do not pretend one canonical feedback schema exists yet.
- Operational Ontology is still a candidate branch and is not runtime retrieval-proven.
- Buyer-facing proof sentence remains a translation layer, not a method primitive.
- Method-specific edge kinds should not be promoted until they add constraints beyond the existing Ontologize/DAG edge catalog.
- `MaintenanceTrigger` needs a field-level schema and owner route before it becomes a first-class method schema.
