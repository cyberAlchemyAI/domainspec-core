## Design Summary

The repository should be organized as a **governed workspace**, not a single-purpose repository.

The stable core is:

```text
implementation/  +  research/  +  validation/
```

The workspace also needs explicit lanes for:

- Arcanum lifecycle source,
- root operations and governance,
- operator/runtime surfaces,
- local product or domain incubators,
- decision-gated knowledge/archive work,
- generated and private runtime state.

The most important design rule:

> A path is not canonical merely because it contains useful files. It must have a current owner, a current name, and no newer canonical successor.

## Runtime Surface Policy

Runtime surfaces are not normal source zones. They are facades or generated installs over canonical source.

### Surface Kinds

| Surface kind | Examples | Mechanism | Rule |
| --- | --- | --- | --- |
| `canonical-source` | `arcanum/arcana/*`, `arcanum/spells/*`, `implementation/domainspec/copilot/skills/*` | source files | Edit here first. |
| `same-checkout-discovery-facade` | `arcanum/.agents/skills/*`, possible root `.agents/skills/arcanum-*` | symlink | Use when source and consumer share a checkout and runtime follows links. |
| `skill-runtime-surface` | `.github/skills/*`, `/mnt/c/Users/vlad_/.codex/skills/arcanum-*`, possible `.agents/skills/*` | skill wrapper or symlink facade | Default install and discovery layer. |
| `command-compat-adapter` | `.codex/commands/*.md`, `.arcanum/runtimes/codex/commands/*.md` | generated file | Not required by default. Keep only with documented runtime need and regeneration path. |
| `machine-global-install` | `/mnt/c/Users/vlad_/.codex/skills/arcanum-*` | managed snapshot | Audit from repo; mutate only in machine-global Codex task. |
| `repo-local-install` | root `.github/skills`, `.arcanum/runtimes/github-copilot/skills` | manifest-backed snapshot/config | Keep only with provenance. |
| `submodule-local-install` | `implementation/domainspec/.github/skills`, `implementation/domainspec/.arcanum` | submodule-owned | Do not parent-edit. |
| `project-local-install` | `projects/*/.github/skills`, `projects/*/.arcanum`, `projects/*/.Codex` | manifest-backed snapshot or cleanup candidate | Needs project admission metadata. |
| `generated-observability` | JSONL ledgers, reflection state, run folders | generated state | Ignore or untrack unless promoted. |
| `local-private-state` | auth, config, model cache, private runtime homes | local state | Never track. |

### Symlink Rule

Use symlinks only for same-checkout discovery facades.

Use managed snapshots for:

- global Codex home,
- GitHub Copilot skills,
- cross-repository installs,
- packaged or distributed runtime surfaces.

Do not create command snapshots unless a runtime-specific compatibility task proves they are still required.

Every managed snapshot needs provenance:

```yaml
surface_id: arcanum-skill-runtime
surface_kind: repo-local-install
installed_from: arcanum/tools/bootstrap_arcanum.sh
source_owner: arcanum
runtime: github-copilot-or-codex-skill
target_paths:
  - .github/skills/arcanum-*
mutation_policy: regenerate-from-source
tracked_policy: generated-install
last_verified: YYYY-MM-DD
```

## Six Design Views

### 1. Context View

`domainspec-core` is the parent workspace for multiple related but differently governed systems:

- DomainSpec implementation source and framework governance.
- Research programs and evidence pipelines.
- Validation harnesses and runtime case studies.
- Arcanum lifecycle source and runtime/bootstrap tooling.
- Local product/domain incubators.
- Machine-global Codex and runtime install surfaces.
- Generated observability and execution state.

The design must let these coexist without turning every copy or generated surface into source.

### 2. High-Level Structure View

The repository has four governance layers:

```text
root workspace governance
  -> canonical source zones
    -> runtime/install surfaces
      -> generated/local state
```

Root workspace governance lives in `ops/`, `docs/`, `tools/`, and the root README.

Canonical source zones are `implementation/`, `research/`, `validation/`, and `arcanum/`.

Runtime/install surfaces are `.agents`, `.github/skills`, `.arcanum/runtimes`, project-local installs, and machine-global Codex home. `.codex/commands` is a legacy command compatibility surface, not a target layer.

Generated/local state is `.data`, `output`, runtime ledgers, caches, private Codex home state, and generated run folders.

### 3. Low-Level Components View

The design needs these concrete components:

- `ops/REPOSITORY-ZONE-CONTRACT.md`: canonical zone definitions and top-level classification.
- `ops/RUNTIME-SURFACE-POLICY.md`: source vs install vs generated vs private-state policy.
- `ops/runtime-surface-inventory.json`: optional generated inventory of runtime surfaces.
- `ops/DELETION-CANDIDATE-LEDGER.md`: approved/pending cleanup candidates.
- root README update: current workspace map.
- organization check: flags unclassified paths, unmanaged installs, and generated-state leakage.
- project admission metadata: explains each `projects/<id>` status.

### 4. Workflow Process View

```text
scan repository
  -> classify top-level zones
  -> classify runtime surfaces
  -> identify deletion candidates
  -> run preservation diffs
  -> decision-gate unresolved owners
  -> create policy artifacts
  -> add validation checks
  -> apply approved cleanup
  -> refresh README/navigation
```

No migration or deletion happens before classification and preservation review.

### 5. Decision Flow View

For each path:

1. Is it canonical source?
   - Keep and protect.
2. Is it a same-checkout discovery facade?
   - Prefer symlink and validate link health.
3. Is it an installed runtime surface?
   - Keep only with manifest/provenance, otherwise classify as cleanup candidate.
4. Is it generated or local/private state?
   - Ignore/untrack unless explicitly promoted.
5. Is it obsolete or superseded?
   - Run preservation diff, then delete if approved.
6. Is owner unclear?
   - Route to decision-gate.

### 6. Dependency Interface View

Key interfaces:

- Arcanum source -> `.agents/skills` symlink facades when the consumer shares the checkout.
- Arcanum source -> skill wrappers under `.github/skills` and machine-global Codex skills.
- Arcanum source -> command adapters only for documented legacy compatibility.
- Arcanum source -> GitHub Copilot skill snapshots where required.
- DomainSpec `copilot/skills` -> DomainSpec `.github/skills` install target.
- Root organization policy -> project admission metadata.
- Runtime policy -> deletion-candidate ledger.
- Machine-global Codex home -> audit-only inventory from this repo.

## Risks

| Risk | Impact | Guardrail |
| --- | --- | --- |
| Deleting a stale-looking path with unique content | irreversible knowledge loss | preservation diff before deletion |
| Treating installed command snapshots as source | source drift | skills-first policy and command-adapter deletion by default |
| Symlinking across Windows/WSL or global Codex boundaries | brittle global setup | managed snapshots for global installs |
| Parent repo mutates submodule-owned surfaces | dirty submodule and ownership confusion | submodule-local surfaces are owner-controlled |
| Generated telemetry remains tracked forever | noisy repository and false source | generated-state untracking plan |

## Glossary Consistency

| Term | Meaning |
| --- | --- |
| Zone | A top-level repository family with an owner and admission rule. |
| Runtime surface | A skill, adapter, hook, or runtime folder exposed to an agent/runtime. Command files are legacy compatibility adapters only. |
| Canonical source | The authoritative source for behavior or documentation. |
| Discovery facade | A thin path that exposes canonical source to a runtime, often by symlink. |
| Managed snapshot | A generated copy with provenance and refresh path. |
| Generated state | Output, telemetry, run state, cache, or database produced by tools. |
| Preservation diff | Review proving unique content is migrated, retained, or intentionally discarded before deletion. |

## Design Decisions

- Keep `domainspec-core` as a governed multi-family workspace.
- Keep the DomainSpec triangle: `implementation/`, `research/`, `validation/`.
- Treat `arcanum/` as the canonical Arcanum lifecycle source.
- Treat `sigils-library/` as a superseded-name deletion candidate.
- Add runtime-surface ownership as a separate layer.
- Use symlinks only for same-checkout discovery facades.
- Use managed snapshots for machine-global, cross-runtime, and distributable skill surfaces.
- Do not keep repository command files as a default layer; prefer skills.
- Do not parent-edit DomainSpec submodule installs.
- Do not treat generated state as source by default.
