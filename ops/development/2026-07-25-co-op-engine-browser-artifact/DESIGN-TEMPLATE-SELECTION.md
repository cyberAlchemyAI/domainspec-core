# Design Template and Profile Selection

## Inventory Evidence

| Candidate | Evidence | Eligibility | Selection |
| --- | --- | --- | --- |
| DomainSpec architecture profile | `arcanum/spells/invoke/design.md` names it as the authoritative normal-Design baseline; `templates/domainspec-spec/architecture-bundle.md` provides all six views | approved Define outputs and exact source contracts exist | selected |
| Architecture family | `templates/architecture/architecture.md` covers source contracts, dependency/interface rules, decisions, and risks | the target introduces a new application boundary and deployment interface | selected as companion structure |
| UX plan | `templates/ux-plan/ux-plan.md` requires a natural person plus a new or changed rendered semantic contract | technical builders, domain practitioners, project owners, participants, and facilitators act through new browser surfaces | selected; validator must emit `ux-plan` |
| Research | Design contract selects this only when architecture evidence is absent, contradictory, or insufficient | accepted two-loop research and user decisions close the product frame | not selected |
| Spell or sigil family | target must be an Arcanum spell or sigil | target is an ordinary browser product | not selected |

## Result

The DomainSpec six-view architecture profile plus Architecture and UX
companions is the only eligible normal-Design combination. There is no
template tie requiring another user decision. Template status establishes
authoring eligibility only; the deterministic Design selection receipt
controls the extension set and Plan route.
