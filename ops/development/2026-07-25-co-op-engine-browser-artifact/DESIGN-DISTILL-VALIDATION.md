# Design-Unit Distill Validation

## Run

- Mode: standard
- Proposal tracks: one
- Recursive rounds: two of two
- Roles: parent-labeled Proposer and Balancer
- Evidence state: Design artifacts only

## Round 1

- Proposer: treat the entire browser product, interaction loop, persistence,
  fourteen cards, copy, audits, meeting, and deployment as one Design unit.
- Balancer: that unit hides three different trust boundaries—record truth,
  semantic projection, and governed interaction—and would make the first Plan
  task impossible to review independently.
- Reconciliation: keep one architecture because the same record/state/privacy
  model must recompose, but layer its implementation witnesses.

## Round 2

- Proposer: begin with the self-guided Poker card because it gives visible
  progress.
- Balancer: rendering first would encode field and state assumptions before
  the hardest invalid-transition and hidden-field boundaries are executable.
- Reconciliation: the smallest coherent first unit is the **Poker shared-record
  contract**—schema, policy version, claim ceiling, state distinctions,
  visibility classification, and known-good/known-bad fixtures. It has no
  browser or deployment dependency and recomposes into every later view.

## Recomposition Proof

```text
Poker record contract
  + visibility projection
  + self-guided renderer
  + facilitated renderer
  + reciprocal state machine
  + persistence/gateway
  + fourteen admitted records
  + copy and human audits
  + meeting/deployment receipts
= approved Co-Op Engine browser artifact
```

Removing the first unit would leave all views without a falsifiable truth and
state boundary. Adding UI, persistence, copy, or deployment would introduce a
second independently reviewable behavior.

## Checks

| Check | Result |
| --- | --- |

`pass`. Design may route to acceptance review and, if accepted, Invoke Plan.
The first Plan SWU should remain `SWU-COOP-001`; Plan must still materialize its
exact file scope, commands, fixtures, stop conditions, and receipts.
