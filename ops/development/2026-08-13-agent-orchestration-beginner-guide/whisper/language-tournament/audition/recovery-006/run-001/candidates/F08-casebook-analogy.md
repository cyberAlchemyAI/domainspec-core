# F08 — Casebook spine × mapped analogy

## Candidate card

- Design claim: the clearest case and the clearest limited analogy can be selected independently for each route, while one repeated causal question keeps the guide coherent.
- Casebook spine: product release, editorial evidence desk, and building-work handoff.
- Repeated question: **What changed, and what still has not?**
- Proposer evidence: analogies are disposable boundary objects; exact terms replace them immediately after use.

## Route 1 sample — opening, two work cards, shared attempt, branch explanation, formal reveal, transfer, claim limit

### Opening

A booking button disappears on small screens. Separately, account deletion needs privacy and accessibility judgments that remain visible on their own. What changed between the requests, and what still has not? The safeguard differs; permission to change anything remains absent.

### Two work cards and shared attempt

**Card A:** return one reproducible cause with screenshot, file, and line; make no edit.

- One investigator returns one evidence report for the lead to inspect before deciding.
- Two reviewers return separate evidence reports for the lead to compare before deciding.

Binding: `choose-one`; values `helper`, `dispatch`; expected `helper`.

**Card B:** preserve separate privacy and accessibility reviews before the lead decides.

- One investigator returns one evidence report for the lead to inspect before deciding.
- Two reviewers return separate evidence reports for the lead to compare before deciding.

Binding: `choose-two`; values `helper`, `dispatch`; expected `dispatch`.

Shared action: **Check both decisions**.

### Branch explanation

- Card A, correct: Yes. One bounded diagnosis returns the whole inspectable result this request needs.
- Card A, corrective: More people do not create another responsibility; identify the second judgment before adding a role.
- Card B, correct: Yes. Each review protects a distinct release obligation.
- Card B, corrective: One combined judgment removes the separation the release lead needs to inspect.

Use a **repair bench** for the first relation and a **two-key control** for the second. The bench maps one fault to one inspectable diagnosis; the keys map responsibilities that cannot substitute. The comparison does not say every dispatch is independent approval, and neither image grants authority. Drop both images at the formal names.

### Formal reveal

1. **boundary** — a decision, permission, or responsibility that must stay separate.
2. **bounded helper** — one person with one clearly limited job whose result the parent can inspect.
3. **governed dispatch** — coordinated work with separate roles, checks, and stop points.
4. **authority** — permission to make a change or claim.

What changed? The responsible shape. What still has not? No route is authorized, recorded, or started.

## Route 3 sample — concrete returned-result problem, predecessor attempt, branch explanation, exact nine-state reveal, limit attempt, loop and closeout, claim limit

### Concrete returned-result problem and predecessor attempt

An editor expects a fact-check, a legal review, and a source-attribution review before publication planning. The fact-check file returns. What changed? One expected record exists. What still has not? The full checked set is not necessarily included for the decision.

- The request to start has a recorded outcome.
- One returned record matches its expected identity and shape.
- Every required checked record is included in the decision's evidence set.

Binding: `relay-predecessor`; values `host-result`, `receipt-admitted`, `receipt-joined`; expected `receipt-joined`.

### Branch explanation

- Correct: Yes. The publication-planning rule needs all required checked records together.
- Corrective: A start outcome or one checked file is earlier than the complete decision set.

Think of an **evidence folder crossing nine labeled desks**. Each desk maps one newly recorded fact; crossing desks does not make the report true. The runtime is not an office and records do not advance themselves. Drop the desks now and use exact states.

### Exact nine-state reveal

1. **Action persisted** — An exact bounded job is saved. The runtime has not been asked to start a worker.
2. **Attempt recorded** — Intent to invoke that exact action is recorded. The runtime has not accepted it and no worker is established.
3. **Host result recorded** — The runtime's start result is recorded. A started worker has not necessarily finished.
4. **Terminally accounted** — The worker's finish, failure, or stop is recorded. Returned work has not entered the evidence set.
5. **Receipt admitted** — The expected record's identity and shape were checked. Its contents are not proved and it has not joined the decision set.
6. **Receipt joined** — The admitted result is included with every required decision input. No gate has necessarily passed and its claim is not thereby correct.
7. **Gate decided** — The declared decision rule was applied. A passing decision does not start the eligible wave.
8. **Dependent plan persisted** — Exact actions for the dependent wave now exist. None has been attempted; each action re-enters this lifecycle.
9. **Terminal closeout recorded** — The route has a final resolution or explicit stop. No canonical status, publication, deployment, production readiness, or truth follows.

### Limit attempt, dependent loop, and closeout

The decision permits layout work to be planned. What must exist before a dependent worker starts?

- Nothing; gate passage starts the worker.
- A fresh persisted action plan for the eligible wave.
- Proof that the earlier receipt is semantically true.

Binding: `relay-limit`; values `nothing`, `new-plan`, `truth`; expected `new-plan`.

- Correct: Yes. Eligibility still needs an exact persisted action.
- Corrective: The decision opens a transition but cannot create or execute the dependent job.

What changed? Eligibility. What still has not? No new worker action has been attempted. The **dependent-work loop** repeats the lifecycle; the **terminal-closeout branch** requires resolution or explicit stop.

## Route 7 sample — concrete handoff, provisional four-link retell, binary attempt, branch explanation, formal mapping, correction and save, claim limit

### Concrete handoff and provisional four-link retell

A building owner receives checked structural and access reviews. The decision permits a ramp repair to be planned, but the maintenance manager has not written a work order.

Draft:

1. `exit-situation` / `situation` — received work and checked results.
2. `exit-present` / `present` — decision and present change.
3. `exit-missing` / `missing` — permitted move and missing work order.
4. `exit-human` / `human` — next owner and remaining limit.

This provisional four-link retell comes first.

### Binary start attempt and branch explanation

Planning is permitted, and no worker input exists. Is current evidence sufficient for work to begin?

- Yes — the owner may use the decision as the worker's start instruction.
- No — the owner must prepare a new bounded work record as the worker's start instruction.

Binding: `transfer-start`; values `yes`, `no`; expected `no`.

- Correct: Yes. The maintenance manager must persist the exact bounded action first.
- Corrective: The decision changed eligibility; it neither wrote the work order nor started a worker.

An **approved permit** is not a **crew's work order**. Approval maps to an eligible next move; the order maps to the exact input a named owner prepares. The analogy does not model host attempts, execution, or truth, and an actual persisted action is not paper. Drop the analogy at the formal mapping.

### Formal mapping, correction, and save

1. **Receipt** — structured record of an expected result.
2. **Admitted** — expected identity and shape checked.
3. **Joined** — all required admitted results included in the decision set.
4. **Gate** — declared decision rule applied.
5. **Persisted action** — exact saved work record required before a host request.

What changed? Planning is eligible. What still has not? The next action, start attempt, and execution. Preserve provisional four-link retell → binary start attempt → branch explanation → formal mapping → retell correction and save. Local presence and the existing minimum-length rule are machine-checkable; a human reviews meaning.

## Guide-wide pattern

Select one literal case and one best-fit analogy per lesson. Repeat **What changed, and what still has not?** State mapping, failure boundary, and drop condition before exact terms. Avoid recurring lore so the analogy, not the cast, carries memory.

## Known risks

- A new case and analogy in each lesson can still create reorientation cost.
- Flexible analogy selection demands stronger editorial review for semantic drift.
- Low lore dependence trades away character attachment and narrative payoff.
