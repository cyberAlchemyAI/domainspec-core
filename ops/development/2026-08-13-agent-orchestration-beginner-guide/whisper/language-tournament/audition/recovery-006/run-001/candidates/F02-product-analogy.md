# F02 — Product spine × mapped analogy

## Candidate card

- Design claim: a recurring product case plus one limited physical analogy per route can make the relation memorable without allowing metaphor to replace exact states.
- Product spine: Priya leads Lantern's billing release; Imani owns eligible follow-on work.
- Proposer evidence: every analogy is introduced after the ordinary problem, states its mapping and failure boundary, and is dropped when exact terms appear.
- Assumption: a beginner benefits from one physical memory hook after a concrete software choice.

## Route 1 sample — opening, two work cards, shared attempt, branch explanation, formal reveal, transfer, claim limit

### Opening

Priya opens Lantern's release board and finds two red cards. Customers receive blank invoice PDFs. A new refund flow also awaits separate finance and accessibility review. “Give both cards to a team,” someone says. Priya needs to know whether the extra role protects a real decision or only adds motion.

### Two work cards and shared attempt

**Card A:** reproduce one blank invoice, identify the failing template and line, and return the rendered file as evidence. Priya will inspect the report; no edit is authorized.

- One investigator returns one evidence report for Priya to inspect before deciding.
- Two reviewers return separate evidence reports for Priya to compare before deciding.

Control binding: `choose-one`; values `helper`, `dispatch`; expected `helper`.

**Card B:** one reviewer checks whether refunds match the amount customers were promised; another checks whether a keyboard user can confirm or cancel. Priya needs both reports separately before release.

- One investigator returns one evidence report for Priya to inspect before deciding.
- Two reviewers return separate evidence reports for Priya to compare before deciding.

Control binding: `choose-two`; values `helper`, `dispatch`; expected `dispatch`.

Shared action: **Check both decisions**.

### Branch explanation

- Card A, correct: Yes. One bounded diagnosis produces the one inspectable result Priya needs.
- Card A, corrective: A second person does not protect another decision here; Priya still needs one cause she can inspect.
- Card B, correct: Yes. Amount accuracy and accessible control are different obligations, so their judgments must remain visible separately.
- Card B, corrective: Combining both reviews inside one judgment removes the separation Priya needs at release.

Picture a **repair bench** beside a **two-key cabinet**. The bench maps to one technician tracing one fault and showing the owner the failed part. The cabinet maps to a responsibility designed so one person's act cannot replace the other's. It does not mean every dispatch requires literal independent approval or that two people create governance; drop the picture once the formal shapes are named.

### Formal reveal

1. **boundary** — a decision, permission, or responsibility that must stay separate.
2. **bounded helper** — one person with one clearly limited job whose result the parent can inspect.
3. **governed dispatch** — coordinated work with separate roles, checks, and stop points.
4. **authority** — permission to make a change or claim.

The invoice diagnosis fits a bounded helper. The refund review fits a governed dispatch. Neither shape grants authority, records a route, or starts work.

### Transfer and claim limit

At a community workshop, one technician identifies a failed projector cable; two counters separately record the donation total. Which safeguard differs? The terms `gate` and `receipt` remain deferred.

## Route 3 sample — concrete returned-result problem, predecessor attempt, branch explanation, exact nine-state reveal, limit attempt, loop and closeout, claim limit

### Concrete returned-result problem and predecessor attempt

The finance review returns report `F-22`. The refund decision requires both `F-22` and the accessibility report. Priya sees the returned file, but she needs to know whether the complete checked set reached the decision.

- The request to start has a recorded outcome.
- One returned record matches its expected identity and shape.
- Every required checked record is included in the decision's evidence set.

Control binding: `relay-predecessor`; values `host-result`, `receipt-admitted`, `receipt-joined`; expected `receipt-joined`.

### Branch explanation

- Correct: Yes. The decision can use the work only after every required checked record is included together.
- Corrective: A start outcome or one checked file is an earlier fact. Find the point where the whole required set is available.

Imagine an **evidence folder moving through labeled trays**. The folder maps to one expected result; each tray maps to a newly recorded state. Moving the folder does not prove what its pages claim, and a real runtime is not a physical mailroom. Drop the folder image at the exact ladder; the state names now carry the work.

### Exact nine-state reveal

1. **Action persisted** — An exact bounded job is saved. The runtime has not been asked to start a worker.
2. **Attempt recorded** — Intent to invoke that exact action is recorded. The runtime has not accepted it and no worker is established.
3. **Host result recorded** — The runtime's start result is recorded. A started worker has not necessarily finished.
4. **Terminally accounted** — The worker's finish, failure, or stop is recorded. Returned work has not entered the evidence set.
5. **Receipt admitted** — The expected record's identity and shape were checked. Its contents are not proved and it has not joined the decision set.
6. **Receipt joined** — The admitted result is included with every required decision input. No gate has necessarily passed and its claim is not thereby correct.
7. **Gate decided** — The declared decision rule was applied. A passing decision does not start the eligible wave.
8. **Dependent plan persisted** — Exact actions for the dependent wave now exist. None has been attempted; each action re-enters this lifecycle.
9. **Terminal closeout recorded** — The route has a final resolution or explicit stop. No canonical status, publication, deployment, production readiness, or truth follows.

### Limit attempt, dependent loop, and closeout

A gate passed. What is still required before Imani's dependent worker can start?

- Nothing; gate passage starts the worker.
- A fresh persisted action plan for the eligible wave.
- Proof that the earlier receipt is semantically true.

Control binding: `relay-limit`; values `nothing`, `new-plan`, `truth`; expected `new-plan`.

- Correct: Yes. Eligibility is not execution; a new exact action must be persisted.
- Corrective: A passing decision changes eligibility only. It cannot create or execute the next action.

The dependent-work loop sends a new persisted action through attempt, host result, terminal accounting, admission, join, and its declared gate. The terminal-closeout branch requires final resolution or an explicit stop; planning is not terminal.

## Route 7 sample — concrete handoff, provisional four-link retell, binary attempt, branch explanation, formal mapping, correction and save, claim limit

### Concrete handoff and provisional four-link retell

Both refund reports are checked and included. The decision permits a correction to be planned, but Imani has not prepared an exact work record for a downstream worker.

Draft the four links before judging whether work can begin:

1. `exit-situation` / `situation` — received bounded work and checked results.
2. `exit-present` / `present` — the decision and present state change.
3. `exit-missing` / `missing` — the permitted move and exact absent worker input.
4. `exit-human` / `human` — the next owner and what remains unproved.

This provisional four-link retell appears before the binary question.

### Binary start attempt and branch explanation

The decision permits planning. No downstream worker input exists. Is current evidence sufficient for the implementation worker to begin?

- Yes — the owner may use the decision as the worker's start instruction.
- No — the owner must prepare a new bounded work record as the worker's start instruction.

Control binding: `transfer-start`; values `yes`, `no`; expected `no`.

- Correct: Yes. Imani still must persist an exact bounded action before a host can be asked to start a worker.
- Corrective: The decision made planning eligible; it did not create a worker's input or attempt a start.

An **approved building permit** is not a builder's **work order**. The permit maps to a decision that makes work eligible; the work order maps to the exact next input. It does not map every legal or runtime step, and approval does not guarantee execution or correctness. Drop the permit picture when the formal chain appears.

### Formal mapping, correction, and save

1. **Receipt** — structured record of an expected result.
2. **Admitted** — expected identity and shape checked.
3. **Joined** — all required admitted results included in the decision set.
4. **Gate** — declared decision rule applied.
5. **Persisted action** — exact saved work record required before a host start request.

Correct the retell, then save. The exact interaction order is provisional four-link retell → binary start attempt → branch explanation → formal mapping → retell correction and save. Local presence and the existing minimum-length rule are machine-checkable; a human reviews meaning.

On expected `no` plus four locally sufficient fields, say exactly: **Exit ticket saved; this lesson is complete.** This is only lesson `lesson-transfer` closeout.

## Guide-wide pattern

Reuse Priya and Lantern for continuity. Let the literal product consequence create the need, add one physical analogy only after the attempt, state mapping and failure boundary, then drop it at the exact vocabulary. Use a changed-domain transfer so recall cannot depend on Lantern lore.

## Known risks

- Three analogies across the representative routes increase reading length and implementation cost.
- The two-key image can narrow dispatch to independent approval if its limit is missed.
- The product spine plus analogy may overdetermine a lesson that literal consequence already explains.
