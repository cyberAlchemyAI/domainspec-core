# F05 — Community spine × mapped analogy

## Candidate card

- Design claim: familiar community work plus one explicitly limited analogy per route can reduce jargon load before the software mapping.
- Community spine: Salma coordinates Riverside Community Hall; Jo handles bounded inspection; Ren owns approved follow-on work.
- Proposer evidence: each analogy follows a literal hall problem and is discarded at the exact formal reveal.
- Assumption: the double transfer—from hall to analogy to software—remains manageable for a beginner.

## Route 1 sample — opening, two work cards, shared attempt, branch explanation, formal reveal, transfer, claim limit

### Opening

Riverside Hall opens for a fundraiser tonight. One exit sign flickers. Separately, the donation closeout needs a cashier's count and an independent second count. Salma has many volunteers, but the number of people is not yet the reason for choosing a work shape.

### Two work cards and shared attempt

**Card A:** Jo identifies the failed exit-sign part, photographs it, and reports. Salma inspects one diagnosis before authorizing any repair.

- One investigator returns one evidence report for Salma to inspect before deciding.
- Two reviewers return separate evidence reports for Salma to compare before deciding.

Binding: `choose-one`; values `helper`, `dispatch`; expected `helper`.

**Card B:** the cashier records the donation total; a second counter records another count without replacing the first. Salma compares both before accepting the closeout.

- One investigator returns one evidence report for Salma to inspect before deciding.
- Two reviewers return separate evidence reports for Salma to compare before deciding.

Binding: `choose-two`; values `helper`, `dispatch`; expected `dispatch`.

Shared action: **Check both decisions**.

### Branch explanation

- Card A, correct: Yes. One inspectable fault report protects every decision in this bounded request.
- Card A, corrective: Another person adds capacity but preserves no second required judgment.
- Card B, correct: Yes. The separate counts exist so one person's number cannot silently stand in for both.
- Card B, corrective: Combining the counts removes the responsibility the second count was meant to preserve.

Think of a **flashlight on one fault** and a **box with two different keys**. The flashlight maps to one bounded investigation; the keys map to responsibilities that cannot substitute for each other. The image does not mean two people create governance or permission, and a dispatch can coordinate roles other than independent approval. Drop the image when the formal terms appear.

### Formal reveal

1. **boundary** — a decision, permission, or responsibility that must stay separate.
2. **bounded helper** — one person with one clearly limited job whose result the parent can inspect.
3. **governed dispatch** — coordinated work with separate roles, checks, and stop points.
4. **authority** — permission to make a change or claim.

The exit-sign diagnosis fits a bounded helper. The two-count closeout fits a governed dispatch. The same safeguard question transfers to software; neither shape grants authority or begins work.

### Transfer and claim limit

In a product release, one person traces one broken button while privacy and accessibility reviewers must report separately. Which relation from the hall still holds? Keep `gate` and `receipt` deferred.

## Route 3 sample — concrete returned-result problem, predecessor attempt, branch explanation, exact nine-state reveal, limit attempt, loop and closeout, claim limit

### Concrete returned-result problem and predecessor attempt

The cashier's signed count returns first. Salma's closeout decision requires both counts checked and present together. One paper in the folder is a result, but not yet the complete decision set.

- The request to begin has a recorded outcome.
- One returned record matches its expected identity and shape.
- Every required checked record is included in the decision's evidence set.

Binding: `relay-predecessor`; values `host-result`, `receipt-admitted`, `receipt-joined`; expected `receipt-joined`.

### Branch explanation

- Correct: Yes. Salma needs both required checked records included together.
- Corrective: A start outcome or one checked count is earlier than the complete decision input.

Picture **nine labeled baskets**, each accepting a record only after one fact changes. The baskets map sequence, not truth: paper in a later basket can still contain a wrong claim. A runtime is not a storeroom and no basket moves work by itself. Drop the picture now; use the exact states.

### Exact nine-state reveal

1. **Action persisted** — An exact bounded job is saved. The runtime has not been asked to start a worker.
2. **Attempt recorded** — Intent to invoke that exact action is recorded. The runtime has not accepted it and no worker is established.
3. **Host result recorded** — The runtime's start result is recorded. A started worker has not necessarily finished.
4. **Terminally accounted** — The worker's finish, failure, or stop is recorded. Returned work has not entered the evidence set.
5. **Receipt admitted** — The expected record's identity and shape were checked. Its contents are not proved and it has not joined the decision set.
6. **Receipt joined** — The admitted result is included with every required decision input. No gate has necessarily passed and its claim is not thereby correct.
7. **Gate decided** — The declared decision rule was applied. A passing decision does not start the eligible wave.
8. **Dependent plan persisted** — Exact actions for the dependent wave now exist. None has been attempted; each action re-enters this lifecycle.
9. **Terminal closeout recorded** — The route has a final resolution or explicit stop. No canonical status, publication, deployment, production readiness, or truth follows.

### Limit attempt, dependent loop, and closeout

The closeout decision permits Ren to prepare follow-on work. What must exist before a dependent worker can start?

- Nothing; gate passage starts the worker.
- A fresh persisted action plan for the eligible wave.
- Proof that the earlier receipt is semantically true.

Binding: `relay-limit`; values `nothing`, `new-plan`, `truth`; expected `new-plan`.

- Correct: Yes. Eligibility is not execution; Ren needs an exact saved action.
- Corrective: A decision cannot create, attempt, or execute its dependent work by implication.

The **dependent-work loop** repeats attempt through the declared gate for every new action. The **terminal-closeout branch** requires final resolution or explicit stop; planning is not terminal.

## Route 7 sample — concrete handoff, provisional four-link retell, binary attempt, branch explanation, formal mapping, correction and save, claim limit

### Concrete handoff and provisional four-link retell

Both counts are checked and included; Salma's decision permits a damaged lock replacement to be planned. Ren owns the next move, but no repair ticket exists.

Draft four links:

1. `exit-situation` / `situation` — received bounded work and checked results.
2. `exit-present` / `present` — the decision and current change.
3. `exit-missing` / `missing` — what may be planned and the absent worker input.
4. `exit-human` / `human` — Ren's next move and remaining uncertainty.

The provisional four-link retell precedes any correctness signal.

### Binary start attempt and branch explanation

Planning is permitted, but no downstream worker input exists. Is current evidence sufficient for the worker to begin?

- Yes — the owner may use the decision as the worker's start instruction.
- No — the owner must prepare a new bounded work record as the worker's start instruction.

Binding: `transfer-start`; values `yes`, `no`; expected `no`.

- Correct: Yes. Ren must persist an exact bounded action before a host can be asked to start a worker.
- Corrective: The decision changed eligibility; it did not create the repair ticket or a start request.

A **room-booking approval** is not the **key handed to the named user**. Approval maps to eligibility; the prepared key maps to an exact next input. The image does not model host attempts, execution, or evidence truth. Drop it when the formal mapping appears.

### Formal mapping, correction, and save

1. **Receipt** — structured record of an expected result.
2. **Admitted** — expected identity and shape checked.
3. **Joined** — all required admitted results included in the decision set.
4. **Gate** — declared decision rule applied.
5. **Persisted action** — exact saved work record required before a host request.

Correct and save in this order: provisional four-link retell → binary start attempt → branch explanation → formal mapping → retell correction and save. Local presence and the existing minimum-length rule are machine-checkable; a human reviews meaning.

With expected `no` and four locally sufficient fields, say exactly: **Exit ticket saved; this lesson is complete.** Only lesson `lesson-transfer` closes.

## Guide-wide pattern

Carry one community location across the guide. Use a literal incident first, one mapped physical comparison second, exact software language third, and an explicit transfer back to repository work. Discard each analogy as soon as the protected vocabulary appears.

## Known risks

- Community story plus analogy plus software transfer creates three representational layers.
- Familiar physical controls may overemphasize independence and underrepresent cooperative dispatch roles.
- Repetition of analogy limits can feel formulaic across seven lessons.
