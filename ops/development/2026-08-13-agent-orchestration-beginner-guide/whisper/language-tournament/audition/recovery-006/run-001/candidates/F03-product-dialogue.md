# F03 — Product spine × decision-room dialogue

## Candidate card

- Design claim: compact product-team dialogue can surface the tempting wrong equivalence before the learner acts, provided narration stays subordinate and choices remain neutral.
- Product spine: Priya, designer Jae, reviewer Cora, and implementation owner Imani work on Lantern's booking release.
- Proposer evidence: every exchange is three turns or fewer and ends in an unresolved decision for the learner.
- Assumption: hearing two credible intuitions helps a beginner locate the responsibility tension.

## Route 1 sample — opening, two work cards, shared attempt, branch explanation, formal reveal, transfer, claim limit

### Opening

Lantern's mobile booking button vanished after a banner change. A separate account-deletion feature awaits privacy and accessibility review.

“Send two agents at the button,” Jae says. “They will finish faster.”

“What second judgment must stay separate?” Priya asks.

Cora points at deletion. “There, two judgments really cannot replace each other.”

Priya turns both cards toward you. Decide from the problem, not the headcount.

### Two work cards and shared attempt

**Card A:** reproduce the hidden button, name the exact file and rule, and return a screenshot. Priya inspects the report before any edit.

- One investigator returns one evidence report for Priya to inspect before deciding.
- Two reviewers return separate evidence reports for Priya to compare before deciding.

Binding: `choose-one`; values `helper`, `dispatch`; expected `helper`.

**Card B:** one report checks truthful data removal; another checks keyboard and screen-reader escape. Both remain separate for the release decision.

- One investigator returns one evidence report for Priya to inspect before deciding.
- Two reviewers return separate evidence reports for Priya to compare before deciding.

Binding: `choose-two`; values `helper`, `dispatch`; expected `dispatch`.

Shared action: **Check both decisions**.

### Branch explanation

- Card A, correct: Priya says, “Yes. One inspectable diagnosis protects every decision this card contains.”
- Card A, corrective: Jae asks, “What would a second judgment protect?” The card names one cause to find, not two responsibilities to preserve.
- Card B, correct: Cora says, “Yes. Privacy cannot answer for accessibility, and accessibility cannot answer for privacy.”
- Card B, corrective: Priya says, “If one voice supplies both judgments, the required separation disappears.”

### Formal reveal

1. **boundary** — a decision, permission, or responsibility that must stay separate.
2. **bounded helper** — one person with one clearly limited job whose result the parent can inspect.
3. **governed dispatch** — coordinated work with separate roles, checks, and stop points.
4. **authority** — permission to make a change or claim.

Jae's speed argument does not create a governed dispatch. The first card fits a bounded helper; the second needs a governed dispatch. Neither choice grants authority or starts work.

### Transfer and claim limit

“Both deletion reports returned,” Cora says. “Can Priya rely on them now?” What must be true before the later decision may use both? Keep `gate` and `receipt` unnamed until Route 3.

## Route 3 sample — concrete returned-result problem, predecessor attempt, branch explanation, exact nine-state reveal, limit attempt, loop and closeout, claim limit

### Concrete returned-result problem and predecessor attempt

“The accessibility report is back,” Jae says, pointing at `A-17`.

“Back is one fact,” Priya replies. “Our decision needs both required reports checked and together.”

“So how far must the evidence move?” Cora asks you.

- The request to start has a recorded outcome.
- One returned record matches its expected identity and shape.
- Every required checked record is included in the decision's evidence set.

Binding: `relay-predecessor`; values `host-result`, `receipt-admitted`, `receipt-joined`; expected `receipt-joined`.

### Branch explanation

- Correct: Priya says, “Yes. The decision sees the complete checked set, not just a returned file.”
- Corrective: Cora says, “That is an earlier fact. Find the point where every required checked record becomes one decision input.”

### Exact nine-state reveal

1. **Action persisted** — An exact bounded job is saved. The runtime has not been asked to start a worker.
2. **Attempt recorded** — Intent to invoke that exact action is recorded. The runtime has not accepted it and no worker is established.
3. **Host result recorded** — The runtime's start result is recorded. A started worker has not necessarily finished.
4. **Terminally accounted** — The worker's finish, failure, or stop is recorded. Returned work has not entered the evidence set.
5. **Receipt admitted** — The expected record's identity and shape were checked. Its contents are not proved and it has not joined the decision set.
6. **Receipt joined** — The admitted result is included with every required decision input. No gate has necessarily passed and its claim is not thereby correct.
7. **Gate decided** — The declared decision rule was applied. A passing decision does not start the eligible wave.
8. **Dependent plan persisted** — Exact actions for the dependent wave now exist. None has been attempted; each action re-enters this lifecycle.
9. **Terminal closeout recorded** — The route has a final resolution or explicit stop. No canonical status, publication, deployment, production readiness, or truth follows.

### Limit attempt, dependent loop, and closeout

“The decision passed,” Jae says. “Then Imani's worker is running.”

Priya pauses. What is still required before that dependent worker can start?

- Nothing; gate passage starts the worker.
- A fresh persisted action plan for the eligible wave.
- Proof that the earlier receipt is semantically true.

Binding: `relay-limit`; values `nothing`, `new-plan`, `truth`; expected `new-plan`.

- Correct: “Exactly,” Priya says. “Eligibility is not execution; Imani still needs an exact action.”
- Corrective: “The decision opens one transition,” Cora says. “It cannot create or execute the next action.”

**dependent-work loop:** a new action re-enters attempt, host result, terminal accounting, admission, join, and its declared gate. **terminal-closeout branch:** only final resolution or explicit stop reaches closeout; a plan is not terminal.

## Guide-wide pattern

Use a recurring product room and at most three short dialogue turns before an attempt. Let each voice carry a plausible intuition, never the answer token. After the branch, retire the conversational dispute and let exact terms carry semantics.

## Known risks

- Dialogue can leak the intended answer by letting the authoritative character state the distinction too early.
- Four recurring names may compete with the nine-state ladder.
- Quoted speech increases reading and screen-reader verbosity without adding a new control.
