## Three-moment construction

### 1. Opening — specific problem and stake

Open at 3:20 p.m. with Priya preparing Lantern's 4 p.m. release. Nora cannot reserve a class on her phone, while the new account-deletion flow still needs review. Give the learner the consequential question in ordinary language: the useful choice is not how many agents sound faster, but what safeguard each request actually needs.

Audience job: enter one scene, understand why a decision is needed, and want to inspect the two work cards. Do not show formal route names, correctness, hidden strings, or a model answer.

### 2. Tension — two concrete work cards and one attempt

Work card A asks for one reproducible diagnosis: exact component or rule, file-and-line reference, and screenshot; no code change. Priya will inspect the report before deciding what happens next.

Work card B asks for two non-substitutable reviews: whether deletion matches the data promise, and whether a keyboard or screen-reader user can safely complete or cancel the flow. Priya needs both separate reports before a go/no-go decision.

Both questions use the same two ordinary-language options with parallel grammar:

1. One investigator returns one evidence report for Priya to inspect before deciding.
2. Two reviewers return separate evidence reports for Priya to compare before deciding.

Keep the shared **Check both decisions** action. The visible options do not use `helper` or `dispatch`; those remain hidden control values. Show only the feedback branch belonging to each submitted answer.

### 3. Reveal — explain, name, limit, and transfer

First explain the branch in the language of each problem. Then compare a repair bench with a two-key cabinet: one supports tracing one fault; the other exists because one person's action must not replace another's. Immediately state the limit: not every multi-person task is a two-key control, and two people without explicit roles, checks, and stops are not thereby governed.

Only then reveal the formal sequence, exactly:

1. `boundary`
2. `bounded helper`
3. `governed dispatch`
4. `authority`

Return to Priya's two cards and map each shape. Add one compact community-hall transfer example, then preserve the changed-movement question about what must be true before Priya may rely on both review reports. Connect the distinction to `arcanum/arcana/subagent-strategy/SKILL.md` without suggesting that reading it grants permission or starts work.

End by transforming the opening question: when someone proposes more agents, ask which safeguard would disappear if roles were combined. Do not claim the learner understood, completed a workflow, gained authority, or proved production behavior.

## Scalable guide-wide story and example pattern

Use a reusable six-beat pattern only where a lesson introduces an unfamiliar relation:

1. **Situation:** one recurring character, place, and immediate condition.
2. **Consequence:** what person, decision, or promise is at risk.
3. **Decision:** one real choice in ordinary language.
4. **Reveal:** the minimum formal vocabulary earned by that choice.
5. **Transfer:** one changed example that cannot be answered by parroting the first.
6. **Repository connection:** source path plus an explicit claim limit.

Apply an example budget so storytelling does not inflate every lesson:

- Reuse Priya and Lantern across related software lessons rather than inventing a new cast.
- Allow at most one anchor episode, two contrast cards, one analogy, and one transfer example in a lesson.
- Give every analogy a mapping sentence and a limit sentence; omit it when the concrete episode already carries the relation.
- Put operational detail behind progressive disclosure when it does not earn the learner's next decision.
- Use lists and tables for exact comparison; use story only for causality, stakes, or responsibility.
- Treat examples as teaching devices, not proof that the repository or lifecycle behaved as described.
