## Route 1 — Work Shape

### Before-Attempt State

#### First visible thought

> **What must stay independent?**

Imagine two requests. In the first, someone needs to find the file and exact
line behind an error; the parent will inspect the report. In the second, two
reviewers must challenge the same proposal separately before a later decision
may use their reports. If you removed an extra role, which request would lose
an important safeguard?

Before either answer is submitted, the learner sees only these situations and
the choices below. Correctness, branch explanations, the four lesson terms,
hidden answer strings, and a model answer remain unavailable.

### Attempt Controls

#### Scenario 1

A request needs the file and exact line behind an error. The parent will inspect
the report before using it.

**Which setup is enough for this request?**

- A single role returns one report for direct parent inspection.
- Different roles return their own reports for a later combined review.

The first visible choice retains hidden value `helper`; the second retains
hidden value `dispatch`. Question `choose-one` expects `helper`. These strings
are control bindings, not visible answer labels.

#### Scenario 2

A proposal must receive two judgments that do not stand in for each other. Both
reports will be considered before implementation planning.

**Which setup preserves what this request needs?**

- A single role returns one report for direct parent inspection.
- Different roles return their own reports for a later combined review.

The same hidden values remain attached to the same visible choices. Question
`choose-two` expects `dispatch`.

Both questions belong to one attempt surface and retain the shared **Check both
decisions** action. Their alternatives use parallel grammar and comparable
specificity, certainty, and emphasis. Submitting reveals only the explanation
for the answer given to that question.

### Feedback Branches

These branches are conditional on their own submitted answer and are absent

| Question | Branch | Explanation shown after that attempt |
| --- | --- | --- |
| `choose-one` | correct | Yes. One limited result that the parent checks directly does not need a coordinated team. |
| `choose-one` | corrective | Ask what the extra role would protect. Here, the parent can inspect one clear result directly. |
| `choose-two` | correct | Yes. Separate judgment and a later decision justify separate roles. |
| `choose-two` | corrective | If one person performed both reviews, two independent judgments would become one responsibility. |

The corrective branches explain the missing distinction without blame and

### Formal Reveal

Only after branch-specific explanation does the lesson name the distinction,
in this exact order:

1. A decision, permission, or responsibility that must stay separate is a
   **boundary**.
2. One person with one clearly limited job whose result the parent can inspect
   is a **bounded helper**.
3. A coordinated job with separate roles, checks, and stop points is a
   **governed dispatch**.
4. Permission to make a change or claim is **authority**.

One bounded helper is enough when one inspectable result protects every needed
decision. Multi-agent dispatch is justified only when the work itself needs
separate judgment, producer/reviewer separation, parallel results, a dependent
decision, or isolated write areas—and it is governed only when those roles,
checks, and stops are explicit.

Choosing either shape does not grant permission, record the route, or start the
work. More agents do not create more authority.

This question requires the learner to transfer the separation rule to evidence

### Formal Reveal

Only after the first branch explanation does the lesson show the entire ladder.
Each row records one changed fact and immediately states what still does not
follow.

| # | Formal state | Changed fact | Immediate non-implication |
| ---: | --- | --- | --- |
| 1 | **Action persisted** | An exact bounded job is saved. | The runtime has not been asked to start a worker. |
| 2 | **Attempt recorded** | Intent to invoke that exact action is recorded. | The runtime has not accepted it, and no worker is established. |
| 3 | **Host result recorded** | The runtime's start result is recorded. | A started worker has not necessarily finished. |
| 4 | **Terminally accounted** | The worker's finish, failure, or stop is recorded. | Returned work has not entered the evidence set. |
| 5 | **Receipt admitted** | The expected record's identity and shape were checked. | Its contents are not proved, and it has not joined the decision set. |
| 6 | **Receipt joined** | The admitted result is included with every required decision input. | No gate has necessarily passed, and its actual claim is not thereby correct. |
| 7 | **Gate decided** | The declared decision rule was applied. | A passing decision does not start the eligible wave. |
| 8 | **Dependent plan persisted** | Exact actions for the dependent wave now exist. | None has been attempted; each action re-enters this lifecycle. |
| 9 | **Terminal closeout recorded** | The route has a final resolution or explicit stop. | No canonical status, publication, deployment, production readiness, or truth follows. |

A persisted action is the exact saved work ticket. The host is the runtime that
receives its prepared request and tries to establish the worker. Terminal
accounting records how that worker ended. A receipt is the structured record
for one expected result; admission checks its expected identity and shape,
while join includes it with every other required decision input. A gate applies
the declared decision rule. An eligible wave is work that may now be planned,
not work that is executing. Closeout records a final resolution or explicit
stop.

Do not compress selected, executing, joined, reduced, gated, and closed into a
single idea. A result can be present without being admitted, admitted without
being joined, joined without a decision, and gated without a dependent action.
