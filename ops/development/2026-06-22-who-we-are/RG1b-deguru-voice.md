## 2. The four principles — de-guru'd public-page copy

Concrete-first, short declaratives, no aphorisms, no name-drops. Peer at a whiteboard.

### Variance lives somewhere — choose where
You can't remove variance from a real operation. You can decide where it sits. Put it in the foundation, where it's monitored and absorbed, and the work on top gets calmer. Leave it scattered, and every layer above pays for it. We learned this the plain way: get the base data right and watched, and the exceptions stop multiplying upward. The good version of a system has fewer special cases, not more rules.

### Build so stress makes it better, not weaker
Rare, expensive surprises happen. We don't pretend to predict them. The question is what a shock does to you. A brittle system breaks. A sturdy one survives. The one worth building gets smarter from the hit — the failure becomes a rule the system now carries, so the same surprise costs less next time. The way you earn that is boring: a small set of foundational rules that stay fixed while everything above them iterates.

### Set conditions, not commands
Rigid rules break under reality's weight. So instead of dictating behavior, we set up the conditions and let the right behavior emerge. It's the same move as running a campaign without hand-defining the audience: give the system good inputs and the right structure, and it finds the right people on its own. Nudge, not cage. It works the same on software, teams, and operations.

### If it needs translating, it isn't done
A system you can't read is a system you can't question — and that's how it quietly concentrates power. So every part should carry its own context: what it is, why it's there, right where you meet it. Not in a separate doc you have to hunt for. How something is presented changes what it can mean; clarity isn't a writing choice, it's a design choice. When a system explains itself as you use it, the work is finished.

## 3. De-guru'd one-paragraph "who we are" thesis

We build systems for people and the agents working alongside them. The aim is simple to state and hard to do: put the complexity into the structure so the person using it doesn't have to carry it. We test things against reality before we trust them, we control what we can actually build and stop fighting what we can't, and we'd rather set the conditions for the right behavior than try to force it. We don't build black boxes — if a system can't explain itself as you use it, we treat the design as unfinished. None of this is theory we're selling you; it's how we've watched good systems behave and bad ones fail.

## 4. The single biggest voice risk — and the rule

**Biggest risk: the universal-truth register.** A "who we are" page invites you to declare what you believe in clean, quotable sentences. That is exactly the guru failure — a conclusion stated from above, polished enough to live on a slide, with the path that earned it stripped out. The manifesto's worst lines ("the beauty of inevitability", "Form is... structurally identical to content") are all this.

**The rule: every belief must trace to something observed.** Before any sentence ships, run the test from `write-style.md`: *if it could sit on a slide deck with no context and still sound coherent, it's posturing, not arguing.* Replace it with the thing that happened — the data that needed watching, the campaign that found its own audience, the exception that disappeared into structure. State conviction on what was lived; hedge on what's only extrapolated. Show the path; let the reader land on the conclusion themselves.
