# Invoke Lifecycle Churn Research

## Agent 1

## Agent: Ashby, W. Ross — internal causal audit

### Finding and proof boundary

The demonstrated defect is not that individual gates are lax. The gates correctly stop unsafe writes. The defect is a lifecycle ownership and transition-model gap that lets a locally valid Plan route to Task Session without the inputs Task Session requires, then uses Refresh both to repair the missing producer boundary and to synchronize mutable planning projections. This conclusion is causal for the DS-SFOL witness and corroborated by BTE; telemetry frequency alone is not causal proof. The current reflection counts 58 Invoke-shaped rows, 30 Refresh rows, and 10 Refresh rows among 13 Invoke rows since July 20, while recording zero Invoke quality-bar failures; it explicitly concludes that local run validity can coexist with lifecycle non-progress (`.arcanum/observability/reflections/20260723T235741Z-invoke-plan-refresh-churn-reflection.md:16-30`). The central projection also omits the later DS-SFOL closeout/rematerialization Refresh, so the cycle is observable only by joining Task Session evidence, the temporary observer envelope, and live targets (`...invoke-plan-refresh-churn-reflection.md:47-51`). Inventory entries are discovery leads only: the reflection reports a machine-readable index but a missing live validator, names the Distill and BTE leads, and states that DS-SFOL has no Inventory entry (`...invoke-plan-refresh-churn-reflection.md:53-65`). Thus Inventory supports where to inspect, not causality or current readiness.

### Causal transition graph

`Define/Design/Plan locally valid` → `Plan identifies SWU and Task Session route` → `Task Session rebuilds live context` → `routed/reusable admission demands exact pre-materialized output bytes + producer receipt + producer schema` → either `admit → one-SWU implementation → live validation → receipt-bound closeout Refresh` or `missing/stale inputs → BLOCK → closeout Refresh/plan repair/materialization → re-enter Task Session`. The loop closes when Refresh mutates exact-byte join targets that remain actively edited projections: `Refresh owner receipt passes` → `later semantic or incidental target edit` → `receipt no longer binds live post-images` → `rematerialize via Refresh`.

The contracts establish every edge. Plan calls `WORK-PACK.md` plus layering the executable baseline, requires approved stable design, and says Task Session owns execution; its automatic Distill gate checks SWU shape and hidden gaps, but its activation inputs do not require a material package or producer receipt (`arcanum/spells/invoke/plan.md:35-58,70-98,125-153`). Task Session requires exactly one current SWU and rejects stale controls (`arcanum/arcana/task-session/SKILL.md:113-146`); immediately before mutation it requires the package, producer receipt, and producer schema, re-reads exact controls, and blocks any absent/stale/mismatched input (`arcanum/arcana/task-session/SKILL.md:220-240`). Refresh apply-approved requires a staged package and validator receipt (`arcanum/spells/invoke/refresh.md:52-70`), validates exact package identity, ownership, publication, paths, dependencies, and commands, but must not execute target tasks (`arcanum/spells/invoke/refresh.md:185-220`). The material schema requires materialized changes to contain exact output references and target inventory (`arcanum/spells/invoke/schemas/material-package.schema.json:58-75,98-149`); its receipt binds package digest, paths, owner/publication results, and validation commands (`arcanum/spells/invoke/schemas/material-package-receipt.schema.json:7-52`). Exact binding is therefore intentional safety, not itself the bug.

### Concrete cycle witnesses

**DS-SFOL (direct causal witness).** Task Session selected one SWU with strict 9/9 context and passed closeout preflight, then blocked before the first write because `materialPackage`, `materialReceipt`, and `producerReceiptSchema` were absent (`projects/domainspec-v2/development/specified-first-order-logic-framework/work-pack/session-evidence/SWU-SFOL-001/20260723T231444Z-independent-denominator/TASK-SESSION-REPORT.md:3-24`). The machine receipt records precisely those three schema failures and `mutationReady:false` (`.../mutation-admission-receipt.json:14-30`). Task Session made no implementation mutation, but routed to Invoke Refresh to materialize the package (`.../execution-receipt.json:33-60,121-129`). The closeout Refresh package then passed all owner/package gates (`.../closeout-material/REFRESH-HANDOFF-RESULT.json:1-34`). Both joined targets subsequently changed; the plan validator still passed, but the owner receipt no longer bound the live bytes, no implementation mutation had occurred, and the route returned to rematerialization (`.../post-closeout-drift.json:1-31`). This proves two distinct causes: absent initial material ownership and later invalidation of an exact join by mutable projections.

**BTE (corroborating but not identical witness).** The full-work Refresh replaced a stale four-layer/ten-SWU projection with L0-L8 and passed extensive validation, yet correctly left the handoff gated and no SWU selected (`projects/domainspec-v2/development/first-production-release/backend-type-test-engine-completeness/refreshes/2026-07-22-full-work-refresh/REFRESH-REPORT.md:5-18,20-40`; `.../refresh-report.json:50-59`). Task Session then blocked because validation-owner red-manifest artifacts were absent, not because of implementation choice (`.../work-pack/session-evidence/SWU-BTE-L0-001/20260722T233617Z-entry-gate-block/TASK-SESSION-REPORT.md:19-29`). A later repair appended one exact LF to nine byte surfaces solely to restore immutable receipt equality, after which Refresh synchronized planning/read models while the next SWU remained blocked on independent evidence (`.../SWU-BTE-L0A-REPAIR-001/20260723T100352Z-exact-byte-repair/TASK-SESSION-REPORT.md:5-24,27-40`). This corroborates stale planning and byte-identity churn, but does not prove all Refreshes share DS-SFOL’s missing-producer cause.

### Earliest detection

1. **Plan activation (earliest preventable point):** once Plan selects a mutation-capable first SWU and route, it knows execution mode, allowed writes, validation surface, and expected receipt class. It should fail the *handoff*, not the authored Plan, if the selected route’s admission inputs or named material owner are absent. Current Plan checks SWU quality but not execution-admission completeness.
2. **Material producer boundary:** before any handoff, the producer validator should prove exact outputs, ownership, dependencies, publication class, and validation commands. Existing validator already does this (`arcanum/spells/invoke/scripts/material_package_validator.py:179-198,202-370`); the gap is invoking it only after a route discovers missing production.
3. **Task Session pre-write gate:** retain unchanged as containment. It is the correct last detector, but too late to be the normal discovery point.
4. **Closeout compare-and-join:** classify live target changes before invalidating lifecycle progress. Exact mismatch must still block apply, but the system needs to distinguish execution-invalidating semantic change from projection-only or unrelated byte drift. Today the signal vocabulary has only coarse `artifact_drift` (`arcanum/spells/invoke/refresh.md:72-98`).
5. **Telemetry:** loop detection is observational, not preventive. Add root goal/epoch/SWU/from-to/mutation-crossed/blocker fingerprint fields only after the owner/transition repair; otherwise it merely labels churn. The current reflection already notes activity rather than progress (`...invoke-plan-refresh-churn-reflection.md:147-153`).

### Public-safe generic invariants (proposed wording, deliberately sanitized)

The private project paths and names above are evidence only and must not appear in public Arcanum contracts. Generic candidate wording:

1. “A mutation-capable handoff MUST name exactly one material producer and one material consumer. The producer MUST emit the schema-valid package receipt the consumer requires; the consumer MUST NOT be the first component to discover that no producer was assigned.”
2. “Authored-plan completion and execution-handoff readiness are independent verdicts. A Plan MAY pass while its handoff is gated, but MUST NOT route to mutation execution until the selected execution mode’s admission inputs exist.”
3. “A selected execution unit MUST bind to an immutable plan epoch containing its controlling contract, dependencies, allowed writes, validation surface, and expected receipts. Mutable human/read-model projections MUST NOT be the sole execution identity.”
4. “Exact digest mismatch always fails closed. The lifecycle effect of mismatch MUST be separately classified as execution-invalidating, projection-only, or unrelated; only proven execution-invalidating change restarts admission.”
5. “Each Refresh run MUST declare one transition kind and one owner-bound postcondition. Projection synchronization, plan repair, material production, and route selection MUST remain distinguishable even if implemented by one spell.”
6. “Run-local validity MUST NOT imply lifecycle progress. Progress requires an observable state transition backed by the owning receipt; repeated same-goal/same-unit returns with unchanged blocker evidence are churn signals, not completion.”

These retain the existing status separation: Invoke already states that artifact authored, registry released, and mutation runtime ready are independent axes (`arcanum/spells/invoke/README.md:54-66`), and the efficiency reflection independently recommends moving falsifiable checks earlier while retaining containment (`.arcanum/observability/reflections/20260723T005559Z-most-used-skills-efficiency-review.md:10-12,39-49,97-106`).

### Smallest candidate fixes and insufficiencies

| Candidate | Smallest useful effect | What it does not solve |
|---|---|---|
| Add Plan handoff-readiness gate requiring named producer + required admission artifacts | Prevents DS-SFOL’s missing-material route from reaching Task Session | Does not decide who produces local implementation bytes; does not prevent post-receipt drift churn. |
| Split admission by execution mode: local Task Session consumes an immutable contract/allowed-write receipt and authors bytes; externally authored/delegated/reusable mutation retains full pre-materialized package | Resolves the demonstrated producer/consumer cycle without weakening reusable mutation verification | Does not stabilize mutable planning joins or classify semantic invalidation. Requires a new local-mode receipt contract and negative fixtures. |
| Add immutable plan epoch / selected-unit snapshot | Separates execution identity from mutable projections | Does not assign the initial material producer or distinguish transition kinds by itself. |
| Add delta-impact class at closeout (`execution-invalidating`, `projection-only`, `unrelated`) | Prevents every byte change from becoming a semantic restart while preserving fail-closed digest checks | Unsafe unless an owner and executable validator prove the class; does not cure missing material. |
| Split Refresh transition kinds | Makes cycles and ownership machine-visible | Renaming alone does not remove a cycle or create a producer. |
| Add progress telemetry and repeated-blocker detection | Detects no-progress recurrence and repairs central/temp observability blind spots | Read-model only; it cannot authorize mutation, preserve receipt binding, or stop the first late discovery. |
| Normalize one machine execution manifest and generate human views | Reduces contradictory mutable surfaces | Larger migration; does not alone solve producer assignment or concurrency and should not be the first fix. |

Recommended minimal research target: combine the first two fixes (handoff completeness plus an explicit execution-mode material owner), then add an immutable selected-unit epoch. Treat impact classification and transition-kind telemetry as the next layer. Do not remove exact digests, weaken fail-closed admission, let Refresh execute arbitrary implementation, or broaden Task Session beyond one SWU. The evidence proves safety controls worked; it proves the ownership/transition arrangement caused avoidable late discovery and restart.

## Agent 2

## External evidence — durable execution and reproducibility patterns

Research performed 2026-07-23; all sources below are official vendor or project documentation.

Durable workflow systems consistently separate a workflow *definition* from a particular *execution*. Azure Durable Functions gives every orchestration instance its own ID, state, inputs, and permanently associated version; its runtime replays history to resume an interrupted execution. It warns that changing the sequence, order, or signatures of old activity calls breaks deterministic replay, and recommends version-aware branches which preserve the old path for existing instances. [Azure Durable Functions: orchestration versioning](https://learn.microsoft.com/en-us/azure/azure-functions/durable/durable-orchestration-versioning) (accessed 2026-07-23). Its storage provider makes the ownership boundary concrete: a history table retains orchestration, activity, sub-orchestration, and external-event payloads, and replays those history events to restore checkpointed state. [Azure Durable Functions: Azure Storage provider](https://learn.microsoft.com/en-us/azure/azure-functions/durable/durable-functions-azure-storage-provider) (accessed 2026-07-23).

Applicable pattern: when `Invoke` turns a proposal into an executable plan, create an immutable execution snapshot with a stable execution ID, canonical plan digest, selected implementation/version, gate inputs, and declared owner. `Task Session` should append explicit transition receipts against that snapshot, rather than “refreshing” the plan in place. A later refresh is then a new revision or a deliberately recorded transition from a specific prior revision—not a reinterpretation of whatever the current planning files say. This is a lightweight lineage rule, not a recommendation to adopt a workflow engine.

Explicit signals are preferable to inferring lifecycle state from incidental file changes. Durable Functions models external input as named events addressed to a specific instance. It also documents an at-least-once delivery guarantee and advises an event ID for de-duplication. [Azure Durable Functions: external events](https://learn.microsoft.com/en-us/azure/azure-functions/durable/durable-functions-external-events) (accessed 2026-07-23). Applicable pattern: represent `approve`, `start`, `handoff`, `refresh-request`, `supersede`, and `close` as named, ID-bearing transitions. A receipt may materialize the effect; it should not silently double as an unversioned command or an inferred authorization.

Retries require idempotence and bounded policy, not a claim that a retry did not happen. AWS Step Functions defines retry policy at the task/state boundary, with error matching, maximum attempts, interval, and backoff; after exhaustion it takes an explicit catcher/fallback transition. [AWS Step Functions: error handling](https://docs.aws.amazon.com/step-functions/latest/dg/concepts-error-handling.html) (accessed 2026-07-23). AWS also notes that a redrive continues from the unsuccessful step while preserving successful prior results and execution history. [AWS Step Functions: redrive](https://docs.aws.amazon.com/step-functions/latest/dg/redrive-executions.html) (accessed 2026-07-23). Applicable pattern: each Task Session action needs an action ID, declared retry policy, and idempotence contract. Retrying a pure validation is different from retrying a mutation; the latter needs an effect key or a receipt proving the intended effect already occurred. Redrive should retain prior successful evidence, not regenerate it to make a current projection look historical.

Concurrent refreshes need a fail-closed compare-and-swap boundary. DynamoDB’s official optimistic-locking guidance uses a version attribute and conditional write: if another process changed the item after the reader observed it, the write fails with `ConditionalCheckFailedException`; the caller must reread before retrying. [DynamoDB: optimistic locking](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/BestPractices_OptimisticLocking.html) (accessed 2026-07-23). Applicable pattern: an Invoke refresh or Task Session transition should commit only if `expectedRevision`/input digest still matches the authoritative ledger or execution snapshot. On mismatch, record a conflict and require re-evaluation; do not overwrite newer state or fold two owners’ decisions into one “refreshed” artifact.

Reproducible-build systems reinforce the materialization boundary. Bazel describes hermetic actions as having known inputs, isolated tools/environment, and an action graph whose hashed inputs drive cache lookup; it names timestamps, host tools, and writing to the source tree as common non-hermetic causes. [Bazel: hermeticity](https://docs.bazel.build/versions/main/hermeticity.html) (accessed 2026-07-23). Nix’s `--check` rebuild comparison exits nonzero when an existing derivation produces a different output and can retain the divergent check output for diagnosis. [Nix Reference Manual: verifying build reproducibility](https://releases.nixos.org/nix/nix-2.15.3/manual/advanced-topics/diff-hook.html) (accessed 2026-07-23). Applicable pattern: make the authoritative input set and owner explicit, generate a materialization only from that set, bind a digest to the result, and treat a byte/digest mismatch as drift evidence—not as permission to overwrite the prior receipt. If a materialization must be replaced, retain the old digest and reason, then issue a new receipt/revision.

Anti-patterns to avoid:

- Mutable “current plan” files treated simultaneously as draft, execution authority, and historical record.
- `refresh` that overwrites a receipt, digest, or approved snapshot and thereby destroys whether a prior run is reproducible.
- Retrying mutating actions without an idempotence/effect key, bounded attempts, and a distinct outcome record.
- Lifecycle changes inferred from filesystem modification time or generated output rather than explicit owner-authorized transitions.
- Last-writer-wins refreshes that do not compare the observed revision/digest at commit time.
- Version changes that retroactively alter the meaning or step sequence of in-flight Task Sessions.

The bounded design inference is: preserve immutable plan/execution receipts, maintain one authoritative current-state projection with compare-and-swap updates, and derive generated views from those records under a named materialization owner. This directly addresses plan–execution–refresh churn while remaining compatible with Invoke and Task Session’s existing document-and-ledger model.
