## Agent 1 — Tversky, Amos

Invoke should select `ux-plan` when a change materially alters a person’s ability to complete, understand, recover from, or trust a workflow—not merely when it is called “UI/UX.” This is consistent with `invoke/design.md`’s existing trigger (“workflow, actor, surface, or accessibility risk”) and its phase-6 gate, while the candidate template currently requires goals, workflow scope, actors, handoff, and accessibility but omits explicit recovery and responsive evidence (`.agents/skills/invoke/design.md`; `arcanum/spells/invoke/templates/ux-plan/{README.md,ux-plan.md}`).

Candidate signals: operator-visible state/projection; an approval, confirmation, reversible, destructive, or recovery path; learner/explanation/navigation flow; user-facing evidence, status, or claim-bound copy; responsive surface changes that can alter meaning; or accessibility-relevant interaction/content. These are human-experience signals, not visual styling: a palette-only or internal component refactor is insufficient. The local Inventory supports this boundary: stale previews/diffs and Accept/Revert required trust and recovery witnesses; the learning map requires distinct learner/navigation projections; mobile layouts can lose semantic meaning; and authored companion status is not completion evidence (`.arcanum/inventory/entries/ui-prototyping-studio-ux-ui-upgrade-research-strategy-result-synthesis.md`; `interactive-ontology-learning-map-strategy-result-synthesis.md`; `domainspec-v2-bte-xray-copy-readability-review-result.md`; `invoke-distill-enforcement-review-strategy-result-synthesis.md`).

Required UX-plan sections for a triggered case: actor goals and constraints; journey/surface/state assumptions; interaction flow including error, confirmation, and recovery; content/claim-bound requirements; accessibility considerations; responsive semantic behaviour where a layout changes; and acceptance evidence with owner. For irreversible or user-controlled-data actions, require a review/confirm/correct or reversibility decision—WCAG 2.2 explicitly requires one of these protections for relevant submissions. Accessibility should be scoped, testable, and integrated throughout production rather than treated as styling; mobile uses the same WCAG basis, not a separate standard. [WCAG 2.2](https://www.w3.org/TR/WCAG22/) (accessed 2026-07-24); [W3C mobile accessibility guidance](https://www.w3.org/WAI/standards-guidelines/mobile/) (accessed 2026-07-24); [ISO 9241-210:2019](https://www.iso.org/standard/77520.html) (accessed 2026-07-24).

Selection should be `required` for known actor/workflow or accessibility risk; `recommended` for inferable, low-risk human-facing changes; and `not-applicable-with-rationale` for backend-only, protocol, data, security, or performance work with no changed human workflow/surface/content/assistive-technology contract. Detect it at design template selection, before architecture handoff; block only when a required core actor/workflow is unknown, otherwise flag the gap. Falsifiable acceptance evidence should include a declared positive journey and failure/recovery journey, explicit accessibility/responsive checks where applicable, and negative fixtures showing that missing actor/workflow, recovery/confirmation, or required accessibility evidence cannot produce `pass`. This preserves the lifecycle rule that authored readiness labels do not substitute for validator-checked evidence (`ops/development/2026-07-24-invoke-lifecycle-progress-update/research/2026-07-24-design-phase-coverage/strategy-inventory-packet.md`; `.agents/skills/invoke/design.md`).

## Agent 2 — van Lamsweerde, Axel

### Finding

Invoke should retain six views as a navigation baseline, but stop treating their presence as architecture sufficiency. `arcanum/spells/invoke/design.md:92-120` blocks only on six-view absence, and `arcanum/spells/invoke/templates/architecture/architecture.md:22-26` validates headings, dependency/interface rules, and a populated decision log. This proves document shape, not that stakeholder concerns are covered or claims are testable. ISO/IEC/IEEE 42010:2022 instead organizes architecture descriptions around viewpoints that address stakeholder concerns; it does not prescribe one universal view set ([ISO, published 2022-11](https://www.iso.org/standard/74393.html); [42010 conceptual model, accessed 2026-07-24](https://www.iso-architecture.org/ieee-1471/cm/)). SEI likewise evaluates architecture against prioritized, measurable quality-attribute scenarios and exposes risks, sensitivity points, and trade-offs, rather than accepting named sections ([SEI ATAM, 1998-04-01](https://www.sei.cmu.edu/library/the-architecture-tradeoff-analysis-method-2/); [SEI quality-attribute scenarios, 2001-09-30](https://www.sei.cmu.edu/library/reasoning-about-software-quality-attributes/)).

### Minimal core

Every architecture artifact should carry only this invariant spine:

1. System-of-interest, scope/ownership boundary, stakeholders, and a `concern_id -> stakeholder -> selected view/section` trace.
2. Components and boundaries with responsibilities, authority/trust assumptions, interfaces, and the runtime mechanism that enforces each normative rule.
3. At least one architecturally significant runtime scenario, selected by risk, with `source/stimulus, environment, affected component, response, response measure`; failure/exception behavior is required when failure changes correctness or authority.
4. Decisions with `status, concern_ids, options, criteria, selected option, positive/negative consequences, trade-offs, evidence, revisit trigger`. The current `Decision | Options | Reason` row at `arcanum/spells/invoke/templates/architecture/architecture.md:82-86` cannot represent consequences, status, or supersession; arc42 explicitly requires important decisions and all consequences, not only positive ones ([arc42 decisions, accessed 2026-07-24](https://docs.arc42.org/section-9/)).
5. A trigger matrix for the extensions below, with exactly `required | recommended | not-applicable-with-rationale`, plus risk owner and earliest validation boundary.
6. Evidence bindings: every architectural claim has `claim_id, concern_id, mechanism_or_contract_ref, validator/check, positive_fixture, negative_fixture, expected_result, owner`. An authored `pass` remains non-authoritative, consistent with `arcanum/spells/invoke/design.md:192-196`.

This is deliberately smaller than a universal checklist. arc42 recommends a representative few runtime scenarios and only the most-needed cross-cutting concepts ([runtime view, accessed 2026-07-24](https://docs.arc42.org/section-6/); [cross-cutting concepts, accessed 2026-07-24](https://docs.arc42.org/section-8/)).

### Risk-triggered extensions and earliest detection

| Extension | Trigger | Required evidence and earliest detection |
|---|---|---|
| Runtime enforcement | Any rule uses “must”, “only”, “reject”, “authorized”, or affects mutation/admission | Map rule to enforcing component, call site/boundary, fail-open/closed behavior, and violating fixture. Detect in Design validation before Plan. |
| Authority/trust | Multiple roles/owners, privilege boundary, delegated/external input, approval, or self-attestation risk | Authority matrix; credential/identity provenance; separation-of-duty invariant; forged/stale/self-issued negative fixtures. Detect at context/interface design. |
| State/event semantics | Lifecycle states, events, replay, supersession, projections, or audit claims | Typed state/event vocabulary, allowed-edge table, terminal/replay/idempotency rules, projection-authority distinction, exhaustive forbidden-edge fixtures. Detect when workflow view introduces the first state/event. |
| Persistence/concurrency | Durable state, multiple writers, retries, queues, caches, or concurrent users | Source of truth, atomicity/consistency boundary, ordering/version token, duplicate/conflict policy, crash/restart recovery, two-writer fixture. Detect at data-store or writer introduction. |
| Failure/compensation | Remote calls, multi-step mutation, partial completion, timeout, retry, or irreversible effect | Failure matrix covering timeout/duplicate/partial success; retry budget and idempotency key; compensation/rollback owner; injected-failure fixture. Detect when the dependency or workflow is selected. |
| Integration/versioning | External API/schema/protocol, independently released producer/consumer, or stored-format evolution | Compatibility policy, negotiation/version field, migration/rollback path, deprecation window, old/new contract fixtures. Detect at dependency-interface design. |
| Deployment/operability | Long-running, distributed, environment-dependent, production-facing, or availability-sensitive system | Environment/topology mapping, configuration/secrets ownership, health/readiness, telemetry/SLO, rollout/rollback, backup/restore where applicable, operational failure drill. Detect when deployment target is known. arc42 makes deployment explicit for distributed systems and relevant environments ([arc42 deployment view, accessed 2026-07-24](https://docs.arc42.org/section-7/)). |
| Data lifecycle | Persistent, sensitive, regulated, derived, cached, exported, or user-deletable data | Data-class/store/owner map; creation, retention, deletion, archival, migration, backup/restore, lineage and disposal rules; lifecycle fixtures. Detect when a data store or durable receipt is introduced. |
| Security/abuse | Untrusted input, trust-boundary crossing, secrets/PII, elevated privilege, external exposure, valuable effects, or resource exhaustion | Data-flow/trust-boundary model, abuse cases, threat/control/verification table, authorization-denial and replay/race fixtures. Detect during context/interface design. OWASP calls for early design-time modeling of flows, stores, external entities and trust boundaries ([OWASP Threat Modeling, accessed 2026-07-24](https://cheatsheetseries.owasp.org/cheatsheets/Threat_Modeling_Cheat_Sheet.html)); NIST says security practices must be integrated into the SDLC ([NIST SP 800-218, published 2022-02](https://csrc.nist.gov/pubs/sp/800/218/final)). |
| Quality/trade-off evaluation | A quality goal is material, competing, costly, or currently expressed only adjectivally | Prioritized measurable scenario, architectural mechanism, sensitivity/trade-off point, risk/non-risk, and evaluation result. Detect before the decision gate or Plan handoff. |

### Counterexamples against the current template

A document can satisfy all current rules while remaining unsafe:

- “Only the transition owner admits changes” appears in a workflow, but no identity source, enforcement boundary, forged-owner rejection, or fail-closed fixture exists.
- “Retry on failure” appears under workflow, but duplicate effects, concurrent writers, ordering, crash recovery, and compensation are undefined.
- “Uses API v1” appears under dependencies, but compatibility, timeout, partial failure, migration, and rollback are absent.
- A database appears as a low-level component, but retention, deletion, backup/restore, lineage, and concurrency policy are absent.
- A risk row names “unauthorized access” and a mitigation, but no trust boundary, abuse case, control owner, or denial fixture exists.
- A decision selects event sourcing “for auditability” without alternatives, operational cost, privacy/deletion consequences, or a revisit trigger.

The lifecycle artifact at `ops/development/2026-07-24-invoke-lifecycle-progress-update/DESIGN.md` demonstrates the stronger pattern: typed contracts (`:51-114`), validator rejections (`:220-233`), fail-closed interfaces (`:291-302`), explicit decisions (`:304-317`), and controls (`:319-330`). It also demonstrates why extensions must be triggered: it covers authority and state/event semantics well, but does not itself prove concurrent-writer behavior, durable recovery, deployment rollback, interface migration, data retention/deletion, or adversarial abuse. Its `Six required views: complete` gate at `:332-341` therefore must not imply those concerns are resolved.

The validator should consequently reject a required extension lacking its trigger-linked evidence, reject unmeasurable quality claims, and reject `not-applicable` without rationale; it should not require inactive extensions. This changes Design from “six headings exist” to “each material concern has a selected viewpoint, enforceable mechanism, falsifiable witness, and owned trade-off.”

## Agent 3 — Ashby, W. Ross

The current package correctly selects an architecture companion for a cross-owner lifecycle change (`ops/development/2026-07-24-invoke-lifecycle-progress-update/TEMPLATE-SELECTION.md`) and already contains migration, telemetry, and privacy-scan gates (`WORK-PACK.md`); it does not justify universal security, SRE, privacy, or support sections. Apply Ashby’s requisite-variety test as a risk-triggered companion decision: the Design contract must represent only environmental variety that could invalidate the declared system boundary, with explicit owner and falsifiable evidence.

- **Security and abuse — architecture companion when** the change adds a trust boundary, credentials, untrusted/retrieved input, privileged mutation, multi-tenant data, external tool, or an economically abusable workflow. Security owns the threat/abuse model and residual-risk acceptance; architecture owns trust/data-flow and enforcement placement; Plan owns implementation and adversarial regression. Earliest detection: Design review. Negative fixtures: authorization bypass, cross-boundary input treated as trusted, replay/out-of-order transition, approval or tool-policy bypass. Otherwise record `not-applicable`: no new trust boundary, privilege, untrusted input, or externally reachable behavior. OWASP places threat modeling in design and requires actionable, testable responses; abuse cases supply concrete tests. [OWASP Threat Modeling Cheat Sheet, accessed 2026-07-24](https://cheatsheetseries.owasp.org/cheatsheets/Threat_Modeling_Cheat_Sheet.html), [OWASP Abuse Case Cheat Sheet, accessed 2026-07-24](https://cheatsheetseries.owasp.org/cheatsheets/Abuse_Case_Cheat_Sheet.html).

- **Privacy and data lifecycle — optional owned privacy/data companion when** personal, sensitive, customer, or regulated data is newly collected, derived, persisted, logged, exported, retained, or deleted. Data steward/privacy owner owns purpose, minimization, retention, disclosure and disposal; architecture owns data-flow and access/erasure boundaries; UX owns meaningful notice, consent and recovery comprehension; Plan/validation own retention and deletion tests. Earliest detection: Design data-flow review. Negative fixtures: secret/PII in receipt or telemetry, undeclared retention sink, deletion that leaves a replica. Otherwise record that no such data crosses or is created by the change. NIST frames privacy risk across collection through disposal. [NIST Privacy Framework, accessed 2026-07-24](https://www.nist.gov/privacy-framework/getting-started-0).

- **Reliability, recovery, performance/capacity, and observability — architecture companion when** a change introduces a runtime service, asynchronous/long-running work, shared dependency, durable state, changed resource profile, or an operator-facing recovery path. Service owner owns SLOs, capacity assumptions, rollback/recovery and incident readiness; architecture owns isolation, failure modes, idempotency and telemetry boundaries; Plan owns load/failure drills and implementation; observability remains non-authoritative, consistent with `DESIGN.md` and `DEFINE.md`. Earliest detection: Design failure-mode review; negative fixtures: dependency outage cannot fail closed or recover, retry duplicates an effect, saturation has no limit/SLO, state transition has no correlatable diagnostic signal. Require an observability companion only if the change creates operational signals or a new operator workflow; use structured correlation and scrub sensitive attributes. [Google SRE Canarying Releases, accessed 2026-07-24](https://sre.google/workbook/canarying-releases/), [OpenTelemetry semantic conventions, accessed 2026-07-24](https://opentelemetry.io/docs/specs/semconv/general/), [OpenTelemetry URL privacy rules, accessed 2026-07-24](https://opentelemetry.io/docs/specs/semconv/url/).

- **Migration, rollout, support and incidents — architecture companion when** compatibility changes, state/data conversion, legacy admission, staged deployment, rollback, or changed support ownership is in scope. This package already triggers the first case through `ILP-G05` and `SWU-ILP-008A` (`GAPS.md`, `WORK-PACK.md`): retain it in architecture, with migration owner defining entry/exit and rollback, and Plan proving no-inference plus rollback/compatibility fixtures. Add an optional rollout/operability companion only for deployed or user-impacting releases: trigger signals are partial exposure, irreversible conversion, external clients, on-call handoff, or support-visible degradation; negative fixtures are incompatible old/new client, failed migration rollback, canary lacking control comparison, and incident without an owner/runbook. Otherwise record that the change is repository-local with no deployed compatibility or support surface. Google’s canary guidance requires limited exposure, evaluation, and release-process integration; its incident guidance requires an advance strategy and regular use. [Google SRE Canarying Releases, accessed 2026-07-24](https://sre.google/workbook/canarying-releases/), [Google SRE Incident Management, accessed 2026-07-24](https://sre.google/sre-book/managing-incidents/).

These are Design-time selection and boundary decisions, not evidence of readiness. Each selected companion must name its owner, trigger, earliest review point, required artifact, negative fixture, downstream Plan validator, and `not-applicable-with-rationale` alternative; absence of a trigger must not manufacture a universal template family.

The evidence supports a risk-triggered assessment, not a new universally required prose section. Design already requires source contracts, template-selection evidence, six views, a Distill check, and an explicit gap route in `arcanum/spells/invoke/design.md`; the missing discriminator is whether those views must additionally cover operator-visible truth, evidence authority, recovery, accessibility, or lifecycle ownership. The proposed assessment should therefore emit `required`, `recommended`, or `not-applicable-with-rationale`, and select/strengthen existing `ux-plan`, `architecture`, `research`, Distill, or decision-gate companions rather than create a new family.

Earliest-detection value is highest before plan/work-pack decomposition: UI state/evidence divergence, receipt-authority conflation, and recovery semantics become multiple downstream SWUs once omitted. The false-positive cost is material for narrow fixtures: the fixture explicitly has no runtime, persistence, or service state and accepts file existence as sufficient evidence (`arcanum/framework/runtime/development/fixtures/invoke-design-artifacts/target/development/ARCHITECTURE-BUNDLE.md`). Likewise, UX is not warranted for the formal generator, whose relevant risk is source/evidence containment rather than an actor surface (`projects/domainspec-v2/development/financial-settlement-executable-test-generation/DESIGN.md`).

Required triggers: external/user/operator-visible state; authorization versus execution claims; persistence/concurrency/recovery; generated evidence or completeness assertions; accessibility/content meaning affecting acceptance. Recommended triggers: reusable architecture alternatives, uncertain source evidence, or future runtime handoff. Not applicable: bounded local artifact work with declared write scope, no actor workflow, no external effect, and a sufficient deterministic witness.
