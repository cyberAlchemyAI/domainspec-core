# Distill Result — Co-Op Showcase Page

- Target context: one local browser artifact used for presentation,
  explanation, and recruitment.
- Objective/output: a finished self-contained HTML page plus validation
  receipts.
- Mode: `standard`, assumed because no explicit Distill budget was selected.
- Proposal tracks: one; parent-simulated Proposer and Balancer.
- Recursive rounds: 2/2.
- Verdict: `pass`.

## Role trace

### Round 1

Proposer: split the work into a portfolio landing page, fourteen project
pages, and a presentation deck.

Balancer objection — hidden glue and truth drift: three surfaces would require
navigation, shared-data synchronization, deployment structure, and separate
presenter copy before the product question is proven.

Reconciliation: use one document with durable project anchors, native
disclosures, and a presentation view over the same records.

### Round 2

Proposer: implement only the three-project minimum research specimen.

Balancer objection — fidelity loss: that unit would test the research
comparison but would not finish the user-requested fourteen-project page.

Reconciliation: retain all fourteen records in one artifact. Keep interaction
small: filters, disclosure, meta cue, and presentation navigation only.

## Smallest coherent unit

`SWU-COOP-SHOWCASE-001`: one truthful portfolio spine containing the opening,
two entrances, fourteen project openings/details, contribution bridge,
presentation view, and validation.

Removing any of those elements breaks the requested combined page:

- without all projects it is not the requested portfolio;
- without details it cannot explain the projects;
- without the contribution bridge it does not recruit;
- without presentation mode it becomes a separate-deck workflow;
- without meta-narration it drops an explicit user requirement;
- without browser/copy evidence it cannot support a completion claim.

## Recomposition proof

The unit recomposes upward into a future hosted site because project anchors
can become routes and the record fields can later become an admitted data
model. The current artifact does not need that machinery to answer the local
page question.

## Deferred complexity

Separate routes, framework/build tooling, CMS, owner workflows, live welcome
state, forms, accounts, analytics, and deployment are deferred because no
current acceptance condition requires them and several cross public/private
boundaries.

## Premortem and guards

- Failure: visual polish hides weak project meaning. Guard: every detail uses
  the same five proof-bounded fields.
- Failure: recruitment copy implies a role is open. Guard: every contribution
  is labelled possible and requires human confirmation.
- Failure: live mode becomes a second deck. Guard: presentation mode only
  changes CSS state over the same DOM.
- Failure: jargon excludes writers or musicians. Guard: plain headings and a
  dedicated terminology/coherence audit.

Frame expiry: choose a routed application architecture when owners admit
current public records, welcome state, and deployment scope.
