# Package Glossary

These terms are package-local design handles. They do not create or promote
canonical Arcanum or CyberAlchemy definitions.

| Term | Meaning in this package |
| --- | --- |
| admission boundary | earliest owner-controlled machine point that may accept or reject a candidate state |
| admissible option | choice that has passed structural and owner-specific preconditions and may be presented to a human |
| acceptance-critical validation | check whose failure or unavailability prevents an acceptance criterion from being claimed complete |
| material package | actual changed paths/content, digests, dependency frontier, owners, mirrors, authorization class, and mutation state proposed for handoff |
| readiness receipt | typed evidence binding one routed mutation request to its current task, sources, dependencies, writes, validation, and authority/publication class |
| status ceiling | maximum state an artifact may claim on one evidence axis; it does not imply a higher or different axis |
| canonical base | lifecycle-owned source from which generated runtime content must derive |
| declared overlay | repository/runtime extension with named extension points, provenance, digest, and a rule that it cannot remove canonical guarantees |
| semantic parity | equivalence of gates, statuses, authority, and required behavior despite allowed metadata or formatting differences |
| projection conformance | agreement among source records, primary machine index, human index, and enabled derived views on identity, coverage, and freshness |
| historical grandfathering | old append-only rows remain readable while stricter admission applies to new inputs |
| protected owner gate | existing human/lifecycle decision that alone may authorize destructive, authority, promotion, publication, spend, or similarly consequential action |
| closure receipt | task-local evidence naming result, artifacts, validation, blockers, residue, and reroute without claiming lifecycle promotion |
