## Why This Layer Exists

CyberAlchemy v2 is the project space where the full definition stack is being
organized. To define lower-level artifacts properly, the top layer needs a small
set of primordial terms that hold across method, representation, communication,
epistemology, Craft execution, and future implementation.

This cluster starts that layer with two user-named bases:

- `orthogonality`
- `recursivity`

## Candidate Voice Sketches

These sketches are intentionally pre-canonical. They are here so the next
definitions-governance pass can promote or revise them without starting from
empty chat memory.

### Orthogonality

Promoted as [CAV2-D29](../DEFINITIONS.md#cav2-d29-axis-orthogonality-invariant).

Scientific/formal sketch: orthogonality is the invariant that two dimensions of
classification, authority, lifecycle, ownership, or validation vary
independently unless an explicit bridge or gate relates them.

Plain-language sketch: two things are orthogonal when moving one does not
secretly move the other.

Domain-context sketch: in CyberAlchemy v2, orthogonality protects distinctions
such as maturity versus promotion, representation versus communication versus
epistemology, source evidence versus local canon, and built status versus
authority status.

Boundary sketch: orthogonality is not isolation. Orthogonal axes can interact,
but the interaction must be named rather than implied.

### Recursivity / Bounded Recursive Self-Application

Promoted as
[CAV2-D30](../DEFINITIONS.md#cav2-d30-bounded-recursive-self-application).
The promoted term is the bounded form; `recursivity` remains an alias for this
guarded meaning, not the vague unbounded label.

Scientific/formal sketch: bounded recursive self-application is the invariant
that a governed process can be applied to artifacts produced by the same
process at a different altitude, while preserving enough shared structure for
validation, provenance, continuation, owner routing, and recomposition.

Plain-language sketch: the system can use its own method to improve its own
method.

Domain-context sketch: in CyberAlchemy v2, recursivity appears when the
definition process defines definition work, when Craft records the work of
operating Craft, and when the intent-to-artifact pipeline can run on earlier
pipeline artifacts.

Boundary sketch: recursivity is not infinite regress. Each recursive step needs
a bounded scope, an artifact, a gate, a next owner, and a recomposition path.

### Primitive Type

Promoted as [CAV2-D31](../DEFINITIONS.md#cav2-d31-primitive-type).

Scientific/formal sketch: a primitive type is a base semantic kind admitted at
the CyberAlchemy v2 authority layer with declared scope, consumers, source
boundary, and specialization rule. It is not derived from a narrower source
space, although it may cite narrower sources as evidence.

Plain-language sketch: it is a base kind the project can build with before it
builds narrower things.

Domain-context sketch: in CyberAlchemy v2, primitive type separates local
primordial terms from programming primitives, DomainSpec meta-types, Arcanum
schemas/contracts, ontology node types, and source-local glossary terms.

Boundary sketch: a lower tower may specialize a primitive type, but it cannot
silently redefine the primitive by using the same word in a narrower context.

### Method

Promoted as [CAV2-D32](../DEFINITIONS.md#cav2-d32-method).

Scientific/formal sketch: a method is a repeatable governance structure with
scope, inputs, actions or phases, roles, gates, outputs, evidence, residue
handling, validation, recomposition, and boundary.

Plain-language sketch: it is how the project repeatedly turns intent and
evidence into checkable work.

Domain-context sketch: in CyberAlchemy v2, method is the umbrella over concrete
methods such as Craft method, reflection tower method, four-facet action
method, and future runtime workflows, without collapsing them into one pipeline.

Boundary sketch: a method can use an engine, pipeline, lifecycle, workflow, or
checklist, but it is not identical to those unless a concrete definition says
so.

### Definition

Promoted as [CAV2-D33](../DEFINITIONS.md#cav2-d33-definition).

Scientific/formal sketch: a definition is the governed semantic unit that binds
a term to a normative meaning inside a declared authority scope, with identifier,
status, aliases, voices, boundary, provenance, consumers, index entry, and drift
route.

Plain-language sketch: it is where the project lets a term finally mean
something.

Domain-context sketch: in CyberAlchemy v2, definition keeps imported source
vocabulary, inventory cards, ontology candidates, handoffs, and source-cluster
rows from becoming hidden authority.

Boundary sketch: a candidate row, source quote, glossary hint, research claim,
inventory card, ontology node, or generated index row can support a definition,
but it is not a definition by itself.

### Typed Coupling Invariant

Promoted as [CAV2-D16](../DEFINITIONS.md#cav2-d16-typed-coupling-invariant).

Definition sketch: when two things cannot remain orthogonal for a decision,
their coupling must become an explicit typed relation with endpoints, direction,
owner, evidence, and effect.

Plain-language sketch: if two things are wired together, draw the wire and
label it.

Domain-context sketch: in CyberAlchemy v2, this protects the project from
letting maturity imply promotion, schema imply contract, source evidence imply
authority, or file proximity imply provenance.

### Reflection Tower Method

Promoted as [CAV2-D17](../DEFINITIONS.md#cav2-d17-reflection-tower-method).

Definition sketch: when residue cannot be closed inside the current schema/data
layer, the residue becomes the seed for a higher explanatory layer with its own
schema, validation, owner, and recomposition path.

Plain-language sketch: when the current floor cannot explain the leftover
problem, build the next floor from that leftover problem and make it explain its
way back down.

Domain-context sketch: in CyberAlchemy v2, this is the primitive method for
climbing from local failure to higher-layer definition, governance, validation,
or ontology work without confusing the reflection tower with ontology or
capability towers.

Formalization sketch: in the Lean-backed DomainSpec evidence, the method is the
promotion move from `L1^n` to `L1^(n+1)` by adjoining `Carrier(mu_n)`, preserving
prior distinctions while adding vocabulary for residue the lower level could not
name.

### Residue

Promoted as [CAV2-D18](../DEFINITIONS.md#cav2-d18-residue).

Definition sketch: residue is the typed remainder exposed by a transformation,
translation, promotion, validation, or governance operation when the target
representation cannot preserve, name, justify, validate, or carry required
source structure.

Plain-language sketch: residue is the meaningful leftover: the part the current
representation could not carry.

Domain-context sketch: in CyberAlchemy v2, residue is the evidence that tells
Craft whether to repair locally, record a typed coupling, route a gate, climb a
reflection tower, accept a tolerated remainder, or defer an open question.

Formalization sketch: DomainSpec uses multiple non-identical residue readings,
including schema residue, instance residue, `ResidueObject`, `ResidueStructure`,
`ResidueCat`, and reflection-tower `Carrier(mu_n)`. CAV2-D18 is the local
umbrella term; subtype claims must be explicit.

### Residue Entropy

Promoted as [CAV2-D27](../DEFINITIONS.md#cav2-d27-residue-entropy).

Definition sketch: residue entropy is a primitive observable for typed residue:
after the operation and residue source are declared, it measures the
distinguishability, uncertainty, or information loss exposed by that residue.

Plain-language sketch: residue entropy tells us how much meaningful distinction
the current layer collapsed or left unnamed.

Domain-context sketch: in CyberAlchemy v2, residue entropy lets Lean-backed
entropy evidence support classification, routing, validation, and research
without treating Boltzmann entropy, retrieval entropy, Gibbs entropy, KL
divergence, or entropy profiles as interchangeable.

Formalization sketch: `Residue.H` supplies the finite Shannon readout on
`ResidueObject`; `EntropyAsFFResidue` supplies the finite microcanonical
Boltzmann bridge `log |fiber|` and positive-entropy/`ffNoise` equivalence;
`SecondLawDiscrete` supplies monotone entropy profiles over finite residue
chains. CAV2-D27 names the observable role, not a replacement for residue.

### Craft Method

Promoted as [CAV2-D20](../DEFINITIONS.md#cav2-d20-craft-method).

Definition sketch: Craft method is a recursive ledger-governance method that
turns bounded work into explicit project state by recording contexts, blockers,
decisions, candidate definitions, validation evidence, typed residue, next
moves, and recomposition obligations in a source-of-truth ledger.

Plain-language sketch: write the state down, name the leftover problem, decide
what can move, and carry the residue forward.

Domain-context sketch: in CyberAlchemy v2, Craft method is the discipline that
lets the Craft execution surface support definition towers, authority imports,
constitution work, research packets, and nested project spaces without turning
candidate state into canonical authority.

Formalization sketch: Craft formal foundations support the method by treating
residue as typed and composable, requiring schema and instance gates to stay
separate, rejecting finite total closure, and allowing stop decisions based on
accepted residue or residue plateau.

### Four-Facet Action Method

Promoted as [CAV2-D21](../DEFINITIONS.md#cav2-d21-four-facet-action-method).

Definition sketch: four-facet action method is the primitive action rule that
every governed action must bind, create, or explicitly residue its
classification/taxonomy, schema, human-continuation view, and
machine-checkable view.

Plain-language sketch: before an action is allowed to matter, answer what kind
it is, what shape governs it, how a human continues it, and how a machine checks
it.

Domain-context sketch: in CyberAlchemy v2, this method applies before or during
definition work, constitution work, axiom work, discipline work, Craft moves,
ontology projections, task execution, workflow design, validation, and
implementation routing. Promotion is only the stricter downstream use case.

Boundary sketch: the method is not a promotion gate and not a perfect-upfront
schema requirement. Missing facets may be created by the action or carried as
typed residue with owner route and continue/defer/block effect.

### Value-Cycle Edge Guard

Promoted as [CAV2-D28](../DEFINITIONS.md#cav2-d28-value-cycle-edge-guard).

Definition sketch: no edge, relation, or ontology movement may both constrain
a value and participate in cycles unless schema governance records an explicit
obstruction review and exception.

Plain-language sketch: an edge can force a value or freely loop; if it does
both, stop and prove the loop is safe.

Domain-context sketch: in CyberAlchemy v2, the useful residue from the AX-ONT
kill memo is not a Lean-to-CAV2 theorem. It is the edge-layer guard that keeps
value-carrying constraints acyclic unless an owner deliberately accepts the
risk, witness, and residue.
