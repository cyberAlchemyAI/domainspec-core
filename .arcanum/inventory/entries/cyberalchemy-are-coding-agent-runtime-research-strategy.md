# CyberAlchemy-v2 and ARE coding-agent runtime research strategy

This is a non-authority read model of an auditor-accepted research result.
It does not adopt BAML or mini-swe-agent,
implement a coding runtime, or grant acceptance, conformance, publication,
deployment, security, or effect authority.

## P1 decision

A governed research dispatch is warranted because the question requires exact
synthesis across at least three materially different source corpora: the live
CyberAlchemy-v2 and ARE implementation, BoundaryML BAML, and mini-swe-agent.
The result also needs independent performance, precedent, and safety attacks.

## Lanes and subagents

- Explorers run in parallel: Shannon maps current CyberAlchemy-v2 and ARE
  ownership and reusable state; Turing examines BAML as a typed model seam;
  Nyquist extracts the minimal mini-swe-agent coding loop and environment seam.
- Wiener synthesizes an exact-binding candidate architecture and measurable
  Ferrari budgets.
- Reviewers run in parallel: Lakatos attacks precedent and dependency fit;
  Popper attacks vacuous speed claims; Taleb attacks security, authority, and
  failure-tail collapse.
- Baez writes the decision-ready findings only after evidence closure.
- Brandenburg audits the final result; the parent remains final approver.

## Dependency flow

`explorers -> synthesizer -> reviewers -> writer -> auditor`, with one bounded
synthesis-to-explorer feedback edge, one synthesizer-reviewer zig-zag, and one
auditor-to-writer revision edge. Whole-sequence loops are capped at two.

## Inventory preflight

The machine index was readable but its package validation was blocked by six
existing source-coverage errors and 169 tag warnings. Selected discovery leads
were the prior audited Codex app-server integration map, its strategy result,

## Result

The surviving hypothesis is to extend existing CyberAlchemy-v2 and ARE owners,
retain Codex App Server as transport, use mini-swe-agent only as a pinned loop
precedent and benchmark, and evaluate BAML only as a pinned parser benchmark.
The benchmark must bind an owner-approved immutable manifest and numerical
quality non-inferiority rules before it is evaluable. Current speed, security,
traceability, reconnect, exactly-once, dependency fitness, conformance, and
production fitness remain `not_evaluable`.
