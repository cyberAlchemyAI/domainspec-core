# Arcanum as a ResonantOS Add-on Research Strategy Result

This is a non-authority Inventory read model of a confirmation-ready research
strategy. It does not confirm or register the dispatch, install or sync
Arcanum, implement a ResonantOS add-on, transfer private DomainSpec or Saturn
authority, deploy anything, promote a capability, or establish release or
production readiness.

## P1 trigger decision

The research is a dispatch because it must synthesize the canonical Arcanum
installer, an already-installed consumer workspace, the nested ResonantOS
product add-on runtime, and browser-first security and validation obligations.
The raw source footprint is larger than the parent should carry, the ownership
and safety claims need isolated checks, and the three explorer lanes can run in
parallel before synthesis.

## Expected end state

The revised strategy targets an implementation-ready contract for a
three-layer composition:

1. Arcanum Bootstrap installs and updates selected public capabilities at the
   workspace or host.
2. ResonantOS exposes them through a native add-on that reuses its existing
   manifest, grant, loopback-host, state, artifact, security, disable,
   rollback, and release owners.
3. Augmentor provides the conversational proposal and control projection.

The intended interaction starts with explicit command precedence and eligible
ordinary-language classification, then a side-effect-free digest-bound
`StrategyProposal`, edit, decline, or explicit approval, owner-backed
execution, targeted child clarification with the parent chat still usable,
reload reconciliation, and a separate choice to open, attach, consume, or
admit each result to memory.

Augmentor must not become a second installer, add-on registry, router,
scheduler, execution owner, workspace, artifact owner, session store, approval
authority, or memory path. The research must select, narrow, or kill this
topology; select the initial public Arcanum capability catalog; and leave exact
contracts, implementation slices, owner decisions, kill criteria, and a
two-child Subagent Strategy plus Whisper browser witness where current
contracts support it.

## Lanes, groups, and subagents

The `explorers` group runs three source- and method-tensioned lanes in parallel:

- `Hewitt, Carl` establishes the canonical Bootstrap and generated-runtime
  contract and the exact state of the existing `../workspace-resonant`
  installation.
- `Simon, Herbert` traces the current `2.0.0-alpha` add-on SDK, manifest,
  capability, registry, bridge, provider, delegation, module, browser, test,
  Augmentor conversation and routing, result-consumption, and cached
  branch-delta owners.
- `Turing, Alan` pressure-tests packaging, secrets, grants, enable/disable,
  Augmentor proposal and approval semantics, updates, rollback, degraded modes,
  release gates, and a literal two-child proposal-to-consumption local fixture.

`Shannon, Claude` synthesizes one exact-binding integration contract. The
parallel `reviewers` group then assigns `Lakatos, Imre` to precedent and owner
duplication, `Gödel, Kurt` to non-vacuity and executable integration, and
`Quine, Willard Van Orman` to definitional, public/private, secret, and
execution-authority non-collapse. `van Lamsweerde, Axel` writes only
`findings.md` after evidence closure. `Brandenburg, Martin` audits it; the
parent remains final approver.

## Dependency flow

The confirmed route is:

`explorers -> synthesizer <-> reviewers -> exact-binding evidence closure ->
writer -> auditor -> parent`.

One feedback edge lets the synthesizer request missing exact source evidence
from explorers, the synthesizer/reviewer zig-zag is capped at two loops, and
one auditor-to-writer feedback edge permits a bounded final repair. Every
spawned agent must be joined and closed. Source repositories remain read-only.

## Exact-binding research obligations

The final research must select, narrow, or kill the intended three-layer
topology and map the current installation, current-versus-target retained
owners, initial public capability catalog, exact manifest, grant, host adapter,
runtime profile, StrategyProposal, approval, command-precedence,
child-interaction, run-tray, state/event, artifact and result-consumption
contracts, update/enable/disable/rollback lifecycle, degraded modes,
public/private and secret boundaries, cached branch delta, ordered
implementation slices, owner decisions and kill criteria, deterministic
checks, and one reproducible two-child proposal-to-consumption browser witness.
Every load-bearing row needs an exact source selector.
