# DomainSpec v2 First Production Release Roadmap Strategy Result

This is a non-authority Inventory read model of the resolved research dispatch
`2026-07-12-domainspec-v2-first-production-release`. It records the approved
roadmap and continuation strategy. It does not ratify a product or supported
profile, assign release owners, promote definitions, mutate implementation,
declare production readiness, authorize release, or change Craft authority.

## P1 Trigger Decision

Dispatch was required by all four Principle-1 triggers: five independent
evidence lenses had to be synthesized; raw repository and external evidence was
larger than the parent context should carry; external production expectations
needed discardable, applicability-tested isolation; and independent formal,
empirical, constraint, technical, operational, and adversarial work could run
in parallel.

The dispatch was `meta: true` because it produced both a first-release roadmap
and a persistent mechanism for researching later frontiers. Persistence means
Craft-backed continuation and separately confirmed child dispatches, not
unbounded autonomous spawning.

## Approved Roadmap Result

The repository does not yet authorize an unqualified DomainSpec-v2 production
designation. The first blocker is **G0**, an externally owned decision that
must name the product lineage, release form, actors, supported profile,
environment, claims, exclusions, compatibility/support boundary, evidence
gates, accountable owner references, and withdrawal route.

The minimum-sufficient candidate is **Option A**: a private, repository-local,
profile-bounded DomainSpec-v2 Validation Toolkit CLI. This is a recommended
inference, not a ratified product contract. Extracted private package, public
derivative, hosted service, supported UI, stable SDK, code generation, and the
full runtime-drift/Saturn loop are separate scope expansions.

The approved dependency route is:

`G0 -> R1/R2 -> R3-R7 -> R8 -> R9 -> R10 -> R12a -> G1 -> G2 -> R11 -> R12b`

- R1 reconciles authority/read-model residue and freezes a clean baseline.
- R2 ratifies the exact supported product/profile contract.
- R3 proves a self-contained compiled runtime.
- R4 makes validation and coverage fail closed.
- R5 makes state mutation contained, recoverable, collision-safe, and
  version-aware.
- R6 decides the bounded security, privacy, dependency, license, and private
  artifact boundary.
- R7 makes the selected CLI operable and supportable.
- R8 installs one exhaustive v2 release gate with deliberate red controls.
- R9 supersedes dirty/conflicting snapshots with clean candidate proof.
- R10 runs a non-author controlled pilot.
- R12a seeds all known residue into the existing Craft context before claim
  acceptance.
- G1 accepts exact claims; G2 authorizes controlled availability; R11 performs
  the release act; R12b operates the persistent strategy afterward.

Production status does not derive from SemVer. `V1-FREEZE` remains the owned
manifest gate and is distinct from Option-A `RELEASE-SELF-CONTAINMENT`.
External standards are advisory; controls bind only through repository
obligations, selected claims, or credible in-boundary failure consequences.

## Persistent Frontier Strategy

`projects/domainspec-v2/.craft/ledger.yml` remains continuation authority. The
roadmap proposes a child context `CTX-DSV2-FIRST-PRODUCTION-RELEASE`; Inventory
is only its query/read model and the dispatch ledger remains dispatch-lifecycle
authority. No parallel frontier registry is created.

The approved operating states are observed, triaged, researching, proposed,
accepted/rejected/deferred, scheduled, verified, and closed, with explicit
reopen transitions. Applicability, release timing, and work kind remain three
orthogonal scalar axes. Missing owners leave nodes gated; missing reproduction
leaves applicability undetermined; missing proof blocks or narrows the claim.

Mandatory evidence frontiers are FR-01 through FR-05: clean representative
corpus evidence, self-containment, state-safety failure injection, bounded
performance, and user/operator evidence. FR-06 through FR-09 remain
conditional Craft records for runtime convergence, UI, public derivative, and
hosted service; each requires its trigger, a new tensioned sheet, explicit
human confirmation, registration, and closeout.
