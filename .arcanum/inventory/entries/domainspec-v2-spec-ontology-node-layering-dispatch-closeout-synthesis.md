## Accepted Result

The proposed Validation Governance YAML is useful design input for a
DomainSpec-local candidate workflow/provenance envelope. It is not currently a
valid `minted-node/v1`, a DS-D1 feature node, an admitted `Authority Envelope`
kind, an admitted `instantiates` relation, or an authority decision.

The stable architecture boundary is:

```text
consumer-owned node sources
  + admitted kind, formation, relationship, and selected-profile authorities
  -> one generated normalized semantic graph
  -> hash-bound learner and navigation projections
```

Subject-authority documents remain owner-governed references. The current
compiler does not compile or digest them, and citing them cannot promote the
candidate representation.

The research keeps these status axes distinct:

- Validation governance subject status: ratified in its local authority record;
- proposed envelope encoding: candidate;
- DS-D1 kind choice: unresolved;
- formation, relation, and selected-profile admission: not established;
- release admission: not granted;
- evidence and commitment confidence: epistemic metadata only.

## Decisive Fork And Witness Order

The first owner decision is not “add `Authority Envelope`.” It is a falsifiable
kind-formation fork:

1. test whether the existing DS-D1 `Workflow` formation can express the record
   with closed validation and without collapsing subject, encoding, owner,
   confidence, challenge, or residue axes;
2. only on a recorded failure, propose a new locally named kind and formation;
3. compile an edgeless same-feature node before admitting any relation;
4. separately select and admit one relation and endpoint role/kind for bounded
   traversal;
5. separately prove an active implementation binding and its derived output;
6. prove semantic-hash invariance for learner/navigation overlays;
7. add cross-feature traversal last.

`Authority Envelope`, `Concept`, and `instantiates` remain provisional input
labels throughout these gates.
