# Arcanum and Codex App Server Audited Integration Map

The audited architecture places Codex App Server as a proposed adapter profile
inside the existing `arcanum/framework/runtime` durable runtime. It does not
create another execution harness, controller, ledger, receipt authority, eval
loop, observability truth, or lifecycle owner.

The official pinned denominator closes at three inbound transports, one
disabled listen mode, one independent outbound connector family, 137 client
requests, 11 server-request variants, 72 notifications, seven user-input
families, and 18 thread-item families. The local 65-technique, 58-schema,
14-generated-package, and eval-evidence aggregates remain open because this run
did not produce exact member ledgers for them.

Ordinary Refine/Task Session adapter use is separate from any future
App Server-backed Orchestrate host decision. Task Session executor evidence,
capability-owner judgment, closeout, Craft ledger apply, Goal bounded rounds,
eval results, observation, and lifecycle promotion stay independently typed.

The research specifies nine deterministic fixture contracts for authoring,
one-SWU execution, one bounded Goal/Craft round, permission pause, stale input,
interrupt/resume, replay mismatch, failed closeout, and no-progress stop. All
nine are `specified-unexecuted`; no App Server runtime witness exists.

`DECISION-LOOP-OWNER-001` remains unresolved between the two current ordered
series reducers. The audited findings therefore support a coherent architecture
and finite Work-Pack frontier only, not implementation or integration readiness.
