# Intent Router Bootstrap and Runtime Integration Research Strategy Result

This is a non-authority Inventory read model of a confirmation-ready research
strategy. It does not confirm, register, or execute the dispatch; install or
generate Arcanum runtime packages; publish private implementation; modify the
orchestrator; promote a reasoning-engine layer; deploy; or release anything.

## P1 trigger decision

This is a dispatch because the answer requires synthesis, context isolation,
and parallel investigation across three separately owned surfaces: public
Arcanum Bootstrap plus generated Claude and Codex runtimes, the nested
cyberalchemy-orchestrator control plane, and the private cyberAlchemy-v2
reasoning-engine stack. Each surface can be researched independently before
one owner-preserving topology is synthesized and attacked.

## Expected end state under test

One transport-neutral resolver accepts normalized intention and a capability
catalog and returns `selected`, `ambiguous`, or `no-route` without executing
work. Arcanum Bootstrap may select, install, update, disable, and generate thin
Claude and Codex wrappers over the same contract. A later
cyberalchemy-orchestrator adapter may consume the result at its input boundary
while retaining dispatch and execution ownership. cyberAlchemy-v2 may integrate
the resolver at the entry-routing layer while retaining private authority.

The research must select, narrow, or kill that topology. A working private
resolver is evidence, not public package authority. Routing alone must not be
described as semantic judgment, object-level inference, actor protocol,
effects, or a whole reasoning engine.

writer -> auditor -> parent`

The synthesizer may request one bounded evidence repair from the explorers.
The reviewer zig-zag is capped at two loops. The auditor may request one

## Inventory preflight

The owner machine index is lookup-ready and validated with zero failures. Four
discovery entries shaped the route:

- the Arcanum-to-ResonantOS add-on result, which separates Bootstrap,
  host-owned runtime truth, and Augmentor projection;
- the orchestrator purpose result, which classifies it as a workflow control
  plane rather than the reasoning engine;
- the agent-reasoning-engine contract result, which separates entry gate,
  actor protocol, and semantic evaluator;
- the Augmentor Subagent Strategy result, which retains Dispatch Spec and
  Orchestrate lifecycle ownership.

Older add-on repair strategies, Augmentor session-fabric proposals, and
authority-memory proposals were excluded because they cannot prove Bootstrap
generation parity or the current reasoning-layer seam. The nested orchestrator
has no machine Inventory, so `target_machine_index_unavailable` remains
residue. Inventory is discovery only; agents must verify current source bytes.

## Design consequences and gaps

The selected design, if evidence supports it, must keep a
transport-neutral resolver core and thin runtime adapters; prove Claude and
Codex behavior parity rather than file presence; keep Bootstrap as installer
and generator rather than semantic owner; consume route proposals at an
orchestrator boundary without creating another scheduler or reasoning engine;
and report reasoning-engine advancement by layer.

Open gaps are public-private extraction and promotion, Bootstrap ownership of
executable bytes versus wrappers, runtime-version and rollback rules,
cross-runtime behavioral parity, the exact orchestrator seam, and the final
reasoning-engine layer classification.
