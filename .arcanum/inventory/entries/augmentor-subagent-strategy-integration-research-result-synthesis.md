# Augmentor Subagent Strategy Integration Research Result

This is a non-authority Inventory read model of an auditor-accepted research
blueprint. It does not implement Augmentor, accept a Resonant runtime profile,
prove the two-child product witness, promote the public Subagent Strategy seed,
import private DomainSpec authority, or establish release or production
readiness.

## Verdict And Use-Mode Matrix

The bounded direction is an additive Augmentor proposal-and-control projection
over existing owners. Public Subagent Strategy supplies lifecycle semantics,
Dispatch Spec validates the frozen route, Orchestrate owns native action
reconciliation, and current ResonantOS delegation, workspace, compute, goal,
provider, artifact, thread, permission, and persistence owners retain their
behavior and terminal truth.

`StrategyProposal` and `RouteDecision` are both
`BUILD-FROM-OWNED + NOVEL-ATTEMPT`: their semantics derive from owned lifecycle
and routing contracts, but no Resonant implementation exists. The current
claim ceiling is `NO_WITNESS_CURRENT`. Bounded implementation and deterministic
fixture work may proceed; execution, user value, performance, readiness,
release, promotion, and production claims may not.

## Public-Neutral Adapter And Runtime-Profile Contract

`StrategyProposal` is a side-effect-free browser-safe projection with stable
role and capability references, bounded inputs and outputs, dependency waves,
gates, stop and loop ceilings, expected handles, permission requirements, a
versioned runtime profile, and a digest over the exact proposal bytes. Editing
or declining it causes no registration, spawn, owner call, or owner Run
mutation.

The consumer profile binds the public lifecycle to current Resonant grants and
native operations. It must fail closed when required operations are absent,
revalidate immediately before launch, and keep private schemas, evidence,
identities, registrar commands, ledger rows, filesystem paths, and secrets on
the server or adapter side.

## Owner, Identity, And Event Mappings

The lifecycle is:

`preview-only proposal -> immutable route decision -> digest-bound approval ->
Dispatch validation and registration -> persisted Orchestrate actions -> one
native owner call per action -> owner-backed transition and outcome
projections -> lifecycle join -> independent delivery and consumption ->
observation`.

UI projections carry opaque owner and evidence references. They never create
execution truth. Lifecycle join is separate from notification delivery, read
state, result consumption, attachment, and memory intake.

## Human Journeys

The proposed interface is a conversational transition card and compact run
tray. It previews exact child roles and boundaries, supports edit or decline
with zero side effects, binds one explicit approval to exact bytes, keeps the
parent composer usable, targets clarification to one child, displays honest
blocked and terminal states, and separates result opening, attachment, and
memory intake. Cancellation remains requested until an owner acknowledges it;
resume creates a new attempt.

## Honest Degraded Modes

Missing required operations hard-block with zero spawn attempts. Validation
failure requires revised bytes and new approval. Serial execution is only a
revised proposal when semantically valid. Augmentor must not invent a queue
when owner capacity is unavailable. Partial outcomes remain independent, and
reload shows unknown rather than fabricating owner truth when reconciliation
cannot reach an owner.

## Ordered Implementation Slices

Refresh the consumer checkout first. Then add neutral proposal, decision,
approval, context, run-correlation, outcome, and hydration projections;
runtime-profile discovery; zero-side-effect preview; digest-bound registration;
one real action-to-owner adapter; owner-aware child admission; two independent
owner bindings; targeted clarification; owner-backed blocker and
reconciliation; cancellation quarantine; and delivery and consumption
separated from memory. Slices before real owner execution are infrastructure
only.

## Exact Deterministic Tests

The blueprint requires zero-side-effect preview/edit/decline, approval
invalidation after byte changes, registration-before-owner-call, exactly-once
action replay protection, projection non-authority, new attempt identity on
resume, marker confinement, child-addressed clarification, owner-backed
blocked and succeeded outcomes, blocked dependent gates, reload reconciliation,
B-only consumption isolation, separate cancellation acknowledgement, complete
lifecycle close, missing-operation hard block, and private-byte scanning.

## Exact Two-Child Browser Witness

The first browser witness uses local-fixture Strategy child A and Whisper child
B. It proves two distinct owner calls while the parent remains usable, thread
switching without reparenting or bleed, one A-only clarification, owner-backed
A `Blocked` with a `blockerRef`, owner-backed B success with an artifact,
dependent-gate blocking, reload reconciliation, and B-only consumption without
changing A, siblings, lifecycle state, or memory. Cancellation is tested
separately and cannot substitute for the blocked-plus-success partial outcome.

## Next Owner Route

Route next to a bounded consumer implementation plan. Resonant capability,
approval, registrar, execution-adapter, projection, context/input,
notification, result, memory, and UX owners must accept their contracts before
implementation. Public Arcanum promotion remains out of scope until audited
medium or complex consumer proof exists.

The reviewer group closed precedent and duplication, non-vacuity, and
authority-collapse concerns. Evidence closure returned `ready`; the auditor
returned `RECOMMEND_ACCEPT`. The original narrative orchestration event log is
retained with its strict-validation failure, while a derived 71-event
owner-evidence causal stream validates `PASS`.
