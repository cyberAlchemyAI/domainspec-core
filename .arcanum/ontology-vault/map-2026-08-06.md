## Selected modeling job

The selected ontology type is `business-system-bridge` because the question is not only what Financial Settlement means or what files exist. The model must show where business intent is realized, which tests cover it, where evidence is absent, and where implementation behavior drifts from the promise.

The existing `ontology.json` remains a separate `architecture-property` ontology. It describes structural implementation properties and is referenced as system-side evidence; it is not replaced or promoted by this map.

## Authority and provenance boundary

The new ontology is a candidate read model with `authority_effect: none`. Its 62 nodes and 155 edges include 52 semantic projection edges and 103 business, DomainSpec, architecture, code, proof-design, and evidence edges. They are backed by machine-readable semantic, DomainSpec meta-type, binding, architecture profile, evaluator, code, and test evidence. Source files support claims about nodes; a file path is not itself the ontology node.

### Reasoning sentence convention

- Current rule before this change: boxes had meaning, status, role, and claim-ceiling text, but no explicit sentence describing the reasoning move permitted by the box.
- Applied rule: every node displayed in the semantic tour lanes owns one `reasoning_sentence`; every highlighted tour subject must resolve to one such sentence or lane explanation.
- Rationale: meaning answers “what is this,” while the reasoning sentence answers “what may I conclude from it, and what must I not conclude.”
- Migration impact: 20 displayed ontology nodes gained the field; the scene resolver now derives per-step reasoning records; the tour panel and node dialog render the same ontology-owned text; validation rejects a missing sentence.
- Affected files: Financial Settlement bridge ontology, ontology validator, scene resolver, HTML canvas, browser/model validator, README, and this map.
- Rollback path: remove the 20 fields and the `missing-box-reasoning` invariant, then remove the derived reasoning records and their two UI projections together. Partial rollback would recreate semantic drift.

### Integration sentence convention

- Current rule before this change: the tour displayed node reasoning sentences, which explained individual boxes but not the typed handoffs between them.
- Applied rule: each tour step owns exactly three structured integration sentences; every supported sentence resolves to one ontology edge, while a `missing-by-design` sentence must resolve to none.
- Rationale: a semantic tour must explain how meaning, formalization, proof structure, architecture, code, and tests connect—not merely define each object independently.
- Migration impact: three lane-handoff edges and two additional highlight edges were added; the second tour step now highlights three connected pairs; the resolver emits integration records and the UI renders their supported or missing direction.
- Affected files: Financial Settlement bridge ontology, ontology validator, scene resolver, HTML canvas, browser/model validator, README, and this map.
- Rollback path: remove the 12 statement records, five new projection edges, resolver projection, tour list, and integration negative control together; restore the previous four-node second step.

## Explicit DomainSpec layer

The ontology now models DomainSpec rather than leaving it in string properties or canvas prose:

- `domainspec.financial-settlement.semantic-graph` contains the typed Financial Settlement meaning.
- `financial-settlement.GenerateSettlement --domainspec.classified_as--> DS-D1.4` records the Operation classification.
- The Calculation, Rule, and Event concepts have corresponding classifications to `DS-D1.6`, `DS-D1.7`, and `DS-D1.12`.
- `domainspec.financial-settlement.obligation-read-model` contains the derived obligations without claiming that they are DomainSpec meta-types.
- `DS-D1.4 --bridge.candidate_maps_to--> architecture.OperationImplementation` makes the candidate implementation-architecture alignment explicit.
- `architecture.OperationImplementation --bridge.shapes_contract--> financial-settlement.OperationImplementationContract` connects the type alignment to the candidate code contract without binding or generating handwritten code.

DomainSpec is represented as a typed sublayer of the bridge model rather than a fourth authority branch. It formalizes and connects the path while business meaning and system evidence retain their separate ownership.

## Claim ceiling
