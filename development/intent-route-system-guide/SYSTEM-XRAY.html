Four honest answers

The resolver is useful because abstention is part of the contract, not an exception hidden behind fallback behavior.

1 · unique fit

Candidate

One route is eligible. ResonantOS may build a proposal, but a human and the existing runtime still control continuation.

2 · information missing

Ambiguous

The system asks the exact discriminating question. No proposal, approval, or run is created.

3 · no known fit

No-match

The route path stops visibly. It does not quietly choose the nearest-looking capability.

4 · contract failure

Invalid

The request or catalog is not trustworthy enough to evaluate. Nothing starts.

Lifecycle stack

Source is not installation

Each lifecycle state proves something different. The current evidence reaches tested candidate packages; consumer enablement remains pending.

  1. Canonical source
    Public resolver, schemas, manifest, fixtures, and JSON port.
  2. Generated package
    Codex and Claude projections validated in isolated use.
  3. Browser + adapter evidence
    Recorded browser witness and local orchestrator acceptance pass.
  4. Consumer install
    Exact package placed at the pinned host entrypoint.
  5. Enable + merge
    Policy activation, product integration, review, and merge remain separate gates.

Risk questions

The decisions still ahead

A clean diagram should make the missing evidence easier to see, not make it disappear.

Which consumer installs first?

The standalone package is portable, but each host still needs an exact install path, pin, policy, and rollback owner.

When should the adapter be enabled?

Only after the installed package bytes match policy and the consumer's review and merge gates pass.

Which ResonantOS route catalog ships?

The planning contract identifies the catalog projector owner; actual product routes and runtime changes are not implemented here.

When can CAV2 claim conformance?

Not until external contract fixtures and owner receipts prove the integrated command, journal, receipt, and read boundaries.
